# brand-shipping-fee — 브랜드가 정하는 고객 부담 배송비

> ⚠️⚠️ **단위가 바뀌었다 — 이 문서의 `shippingKrwOverride`(원)는 지금 `shippingUsdOverride`(USD 센트)다.** PG 청구 통화가 USD 라 원화 고정은 손님 화면에서 환율 따라 흔들렸다(2026-09-30 후속 전환). 결정 5(이름)와 결정 3(입력 통화)만 그만큼 낡았고 **나머지 결정은 전부 그대로 참이다**. 현행 사양은 [`decisions/shipping-seeding.md` 2026-09-30-2](../../decisions/shipping-seeding.md#2026-09-30-2).

## 읽는 순서

1. 이 문서 — **무엇을 왜 이렇게 정했나** (결정 요약)
2. [`implementation-plan.md`](./implementation-plan.md) — **빌드 스펙 정본.** 착수 게이트 · 스키마 · 단계 1~5 · 위험 대장

상태("지금 어디까지 왔나")는 여기에 없다. 정본은 [`../../PROGRESS.md`](../../PROGRESS.md) 하나다.

## 한 문단 요약

브랜드가 무료배송을 켜지 않으면 고객은 배송지 국가의 `SeedingRate` **500g 티어 값 그대로**를
배송비로 낸다(청구 대상 브랜드당 1회). 브랜드가 쥘 수 있는 손잡이가 `ON/OFF` **두 칸뿐**이라,
배송비를 조금만 낮추고 싶은 브랜드도 **전액 부담**(무료배송) 아니면 **전액 전가** 중에서 골라야
한다. 이 트랙은 그 토글을 **0원부터 임의 금액까지의 값**으로 바꾼다. 저장은
`ProductCountryPrice.shippingKrwOverride`(nullable) 한 칸이고, **`NULL` = 지금과 같은 500g 요율**이라
아무것도 설정하지 않은 브랜드의 동작은 불변이다.

## 왜 이게 KLOW 손익을 건드리지 않나

[`decisions/settlement.md` 2026-09](../../decisions/settlement.md#2026-09) 전환으로 **고객이 낸
배송비는 전액 브랜드 정산으로 지급**되고 EFS 실비+수수료는 **브랜드에 전액 후청구**된다. 요율표와
실비의 차액은 **이미 브랜드 손익**이다. 그러니 브랜드가 그 금액을 직접 정해도 KLOW 수지는
달라지지 않는다 — 브랜드가 자기 마진을 스스로 조절하는 형태가 될 뿐이다.

→ **이 트랙이 정산·청구 산식을 한 줄도 건드리지 않는 근거**이고, 실제로 `perBrandShareUsd` 와
그 소비처(송장 EFS 27번 안분 · 브랜드 정산 지급액 · efs-billing 선결제 참고값 · 어드민/브랜드
정산 화면)는 **전부 무수정**이다. `Order.shippingFeeByBrand` 가 이미 브랜드별 금액 맵이기 때문이다.

## 결정 요약

### 1. 세팅 단위는 **제품 × 국가** — 현행 무료배송 토글 자리 그대로 (2026-09-29 사용자 결정)

`ProductCountryPrice` 에 컬럼 하나를 더한다. 브랜드 전체 × 국가로 올리는 안(입력 1회로 끝남)도
검토했으나, 제품별로 무료배송을 다르게 쓰던 기존 설정을 브랜드 단위로 합쳐야 하고 화면 위치도
옮겨야 해서 기각했다.

배송비는 **브랜드 단위로 청구**되는데(한 브랜드 = 한 송장 = 한 박스) 설정은 제품 단위라,
한 브랜드의 라인이 여러 개면 **그중 최댓값 1회**를 청구한다.

**max 가 현행 규칙의 정확한 일반화인 근거.** 지금 라인 값은 `kᵢ ∈ {0, R}` 두 개뿐이고
(무료 → 0, 그 외 → 기본 요율 `R`), 규칙은 *"한 라인이라도 유료면 전액 청구"* 다.

```
max kᵢ = R  ⟺  ∃i: kᵢ = R  ⟺  ∃i: ¬freeᵢ
```

현행 `chargeableBrandIds` 와 **완전 일치**한다. 값의 범위만 연속으로 넓히면 규칙 자체는 그대로다.

기각한 집계들:

| 집계 | 왜 아닌가 |
|---|---|
| `min` | `∃free ⇒ 0` — "한 라인이라도 무료면 브랜드 전체 면제". 현행의 **정반대**이고 배송비가 샌다 |
| 라인별 합산 | "한 브랜드 = 한 송장 = 1회 청구"와 정면 충돌. 5개 담으면 5배 |
| 첫 라인 | **배열 순서 의존** → 비결정적. 지금 코드가 빠져 있는 함정이다(`§4` R1) |
| 브랜드 대표값 | 설정 단위를 브랜드×국가로 바꾸는 것이라 이 결정과 모순 |

### 2. 상한은 정책상 없다. 서버 검증은 **오타 방어 천장 100만원**만 (2026-09-29 사용자 결정)

*"우리는 실배송비를 예상할 수 없다"* — 그 제품의 예상 배송원가(박스 규격 기반 청구중량 요율)를
상한으로 쓰는 안은 **기각**됐다. 브랜드는 요율표보다 **비싸게도** 매길 수 있다.

zod 의 `.max(1_000_000)` 은 **정책이 아니라 자릿수 오타 방어**다(30,000 → 300,000). 요율표 최고가가
수만 원대라 정상 입력은 전부 통과한다. 배송비 100만원은 정책이 아니라 실수다.

### 3. 입력은 원화(KRW) · 손님 화면은 현행 유지 (2026-09-29 사용자 결정)

요율표·원가·마진이 전부 원화라 비교가 쉽다. 결제 시 주문 시점 환율로 USD 환산되는 것은
지금 500g 요율이 처리되는 방식 그대로다(`perBrandShippingFeeUsdCents`).

손님 화면은 **바뀌지 않는다** — `0원`일 때만 기존 '무료배송' 배지가 뜨고, 금액은 체크아웃에서만
보인다. 공개 응답의 `freeShipping` 파생값이 `shippingKrwOverride === 0` 으로 바뀔 뿐이라
klow_web 의 배지 코드는 **무변경**이다.

### 4. `NULL` = 요율표 추종 — 값을 복사해 굳히지 않는다 (2026-09-29 사용자 결정)

설정 안 한 국가는 행을 만들지 않고, 결제 때 그 국가 500g 요율을 읽는다. 그래서 운영팀이 요율표를
갱신하면 미설정 국가는 **자동으로 따라 움직인다**.

설정 시점 값을 복사해 98개국 행을 만드는 안은 기각했다 — 요율표가 올라도 브랜드는 옛 금액만 받아
손해가 조용히 누적되고, 데이터가 `제품 × 98행` 으로 불어난다.

⚠️ 그래서 **세 상태가 서로 다른 뜻**이다. zod 에 `.default()` 를 주면 이 구분이 무너진다.

| 값 | 뜻 |
|---|---|
| 행 없음 / `NULL` | 그 국가 500g 요율 (기본값) |
| `0` | 무료배송 (브랜드 전액 부담) |
| `> 0` | 브랜드가 지정한 금액 |
| payload 에 **키 자체가 없음**(`undefined`) | 구 클라이언트 → 기존 값 **보존**(`§4` R2) |

### 5. 이름은 `shippingKrwOverride` — `customerShippingKrw` 를 쓰지 않는다

`customerShippingKrw` 는 **이미 점유된 이름**이다. 서버가 `ShippingCountry` 응답에 붙이는 파생
필드명이 정확히 그것이고(`shipping.service.ts` `withCustomerShipping`), klow_admin·klow_web·klow_brand
**세 프론트가 전부 "그 나라 500g 요율"이라는 뜻으로** 쓴다.

그리고 새 UI 가 살 곳(`PriceStep`/`PriceModal`)은 **기본값(국가 요율)과 오버라이드(제품×국가)를
한 화면에서 동시에** 쓴다 — 같은 이름이면 리뷰에서 구분이 불가능하다. `Override` 가
`NULL = 요율표 추종` 시맨틱까지 이름에 담는다.

### 6. 구 컬럼 `freeShipping` 은 드롭하지 않고 **파생 미러**로 남긴다

`DROP COLUMN` 은 롤링 비안전이다. 대신 `freeShipping = (shippingKrwOverride === 0)` 으로
**함께 쓰되 읽지는 않는다**(`BrandUser.phone` 이 `BrandUserPhone` 의 비정규화 미러인 것과 같은 구조).

정본은 새 컬럼 **하나**다. 미러를 유지하는 이유는 ① DB 를 직접 보는 사람이 stale 한 값에 속지
않게 하고 ② 나중의 드롭을 무해하게 만들기 위해서다. 드롭은 마지막 단계에서 **예약**만 한다.

### 7. 어드민은 제품 폼 + 주문 상세까지. 손익 감시 컬럼은 이번에 안 한다 (2026-09-29 사용자 결정)

- **제품 폼 숫자 입력 교체 — 필수.** 어드민 제품 폼이 `countryPrices` 를 통째로 다시 만드는
  **파괴적 쓰기 경로**라(`§4` R2), 숫자를 표현하지 못하면 어드민이 제품을 저장할 때마다 브랜드
  설정이 날아간다
- **주문 상세에 브랜드별 배송비 표 — 포함.** 지금은 총액만 보여준다. 금액이 브랜드마다 갈리면
  *"왜 이 주문 배송비가 $12인가"* 에 답할 수단이 없다. 서버는 이미 `Order.shippingFeeByBrand` 를
  갖고 있어 응답에 싣기만 하면 된다
- **efs-billing `요율표 대비` 컬럼 — 뺀다.** 브랜드가 배송비를 낮췄을 때 어떤 패턴이 나올지 아직
  모르니, 실제로 적자 행이 보이기 시작하면 그때 더한다.
  ⚠️ **대신 그 탭의 주석은 이번에 반드시 정정한다** — `efs-billing.service.ts` 가
  *"적자가 이어질 때 고칠 곳은 여전히 배송비용 탭의 국가 요율표다"* 라고 단언하는데, 이 트랙
  이후로는 원인이 **브랜드 설정**일 수 있어 **거짓이 된다**

## 운영 실측 — 아직 안 했다

`freeShipping = true` 인 `ProductCountryPrice` 행 수와 그 제품·브랜드 분포는 **1단계 착수 시**
운영 SELECT 로 확인한다. 계획 세션에서는 운영 DB 접속 수단이 없었다(로컬 `.env` 는 dev 브랜치).

⚠️ **dev 브랜치 수치로 판단하지 않는다** — 테스트 데이터가 정반대 결론을 준 선례가 있다
(`storefront-menu-pc` 의 PC 히어로 보유율: 운영 85% / dev 는 정반대 그림).
