# 카페24 자사몰 주문 → 콜로세움 3PL 출고

> 상태는 [진행표](../../PROGRESS.md) 참조. 이 폴더의 문서는 **스펙**만 갖는다.

브랜드가 운영하는 **카페24 자사몰 주문을 KLOW 로 끌어와, 콜로세움 3PL 창고에 맡긴 그 브랜드
재고로 출고**시킨다. [3PL 풀필먼트](../3pl-fulfillment/implementation-plan.md) v1 이 만든
`FulfillmentRequest`·`BrandInventoryItem` 위에 **유입 경로 하나를 얹는 것**이고, 출고 이후
(어드민 콜로세움 엑셀 내보내기)는 기존 경로를 그대로 쓴다.

## 읽는 순서

| 문서 | 정본 범위 |
|---|---|
| 이 파일 | 결정 요약 · 왜 별도 트랙인가 · 착수 게이트 |
| [`flow.md`](./flow.md) | 전체 흐름과 설계 논거 — "왜 이렇게 하나". 대안을 버린 이유가 여기 있다 |
| [`implementation-plan.md`](./implementation-plan.md) | **정본** — 스키마 · 엔드포인트 · 단계별 빌드 스펙 |

## 한 줄

**브랜드가 자사몰을 OAuth 로 연결 → 카페24 상품을 KLOW 제품에 1:1 매핑 → `쇼핑몰 주문 불러오기`
→ 불러온 주문을 골라 출고신청으로 전환(재고 차감) → 기존 3PL 경로로 출고.**

## 확정된 결정

| 항목 | 결정 | 이유 |
|---|---|---|
| 상품 매핑 | **브랜드 수동 1:1** (`Cafe24ProductMap`) | 재고가 KLOW `Product` 단위로 깎인다. 상품명 자동매칭은 **오매칭이 곧 잘못된 재고 차감**이고, 틀린 걸 나중에 알면 이미 창고에서 물건이 나간 뒤다 |
| 주문 저장 | **미러 테이블 → 선택 → 일괄 전환** | 재고 부족·매핑 누락을 **전환 전에** 걸러낸다. 이미 있는 엑셀 `미리보기 → 적용` 과 같은 형태라 브랜드가 배울 게 없다 |
| 재고 차감 | **전환 시점** (불러오기 시점 아님) | 불러오기는 조회일 뿐이다. 잘못 들어온 주문·취소된 주문이 재고를 잡으면 안 된다 |
| 수집 방식 | **수동 `불러오기` 버튼만** | 주문 **자동수집** cron·웹훅은 v1 밖. 쿼터와 중복 판정을 한꺼번에 떠안지 않는다. ⚠️ **토큰 갱신 cron 과 미러 파기 cron 은 별개 축이라 v1 에 들어간다**(refresh token 이 14일이라 없으면 2주 방치된 연동이 전부 끊기고, 미전환 미러의 PII 를 지울 수단이 사라진다) |
| 앱 진입 경로 | **KLOW 스튜디오에서 시작하는 경로만** | 카페24 앱스토어 진입은 몰 관리자 **iframe** 안이라 `klow_brand_sid`(운영 `sameSite:'none'`)가 3rd-party 차단에 걸려 **로그인 상태가 아닐 수 있다**([`flow.md` §8](./flow.md)) |
| 전환 후 취소 | **재전환 불가** (v1) | 되돌리려면 `fulfillment` 모듈의 취소 경로를 건드려야 한다. 화면에서 "다시 보내려면 단건 신청"으로 안내한다 |
| 송장 회신 | **v1 밖** | 콜로세움이 송장번호를 어떻게 회신하는지가 미확정이다([3PL §2 D](../3pl-fulfillment/implementation-plan.md)). 그게 정해지기 전에는 카페24 에 쓸 값 자체가 없다 |
| OAuth scope | **읽기만** — `mall.read_order` · `mall.read_product`(+ `mall.read_store`) | 송장 회신이 빠지면 쓰기 권한이 필요 없다. 심사와 브랜드 동의 문구가 그만큼 가벼워진다 |
| 앱 유형 | **퍼블릭앱**(앱스토어 심사까지 이 트랙에) | 심사 전에는 **최대 5개 쇼핑몰**에만 설치된다. 그 전 단계는 테스트 앱으로 개발·검증한다 |
| 연동 단위 | **브랜드 1 : 카페24 몰 1** | `InstagramConnection.brandId @unique` 와 같은 형태 |

## 왜 3PL 트랙의 다음 단계가 아니라 별도 트랙인가

[3PL 계획서 §5](../3pl-fulfillment/implementation-plan.md) 가 "다음 트랙 후보"로 미뤄 둔 유입은
**KLOW 내부 주문**(일반주문·시딩)이다. 그 항목이 경고하는 것도 *"같은 주문이 주문 탭 '발송 대기'와
출고신청에 이중 노출된다"* 는 내부 축의 문제다. **외부 쇼핑몰 유입은 그 목록에 없는 새 축**이고,
겹치는 코드가 없다 — 이쪽은 `Order`·`Shipment`·EFS 를 아예 만나지 않는다.

진입 기준([PROGRESS §2](../../PROGRESS.md))에 셋이 걸린다: 2세션 이상 · Prisma 마이그레이션 ·
외부 승인 대기(카페24 심사).

## 착수 게이트

⚠️⚠️ **[3PL 트랙](../3pl-fulfillment/implementation-plan.md) 7단계(운영 배포)가 먼저다.** 이 트랙은 `FulfillmentRequest`·`BrandInventoryItem`
위에 얹히는데, 그 테이블은 아직 전용 Neon 브랜치 `ep-floral-sun` 에만 있고 `staging`·운영에는 없다.
세 레포가 `feat/3pl-fulfillment` 브랜치에 머물러 있어, 여기서 새 브랜치를 파면 **머지 기준선이 둘로
갈린다** — 나중에 두 트랙의 마이그레이션 순서를 사람이 기억해서 맞춰야 한다.

⚠️ 그리고 **0단계(카페24 개발자센터 앱 생성)는 사용자 작업**이다. `client_id`/`client_secret` 과
등록된 redirect URI 가 없으면 2단계부터 아무것도 확인할 수 없다.

## 이 트랙이 하지 않는 것

- **유럽 주문 라우팅** — 일반주문을 EFS 대신 콜로세움으로 보내는 축은 [3PL §5](../3pl-fulfillment/implementation-plan.md) 의 별개 후보다
- **콜로세움 물류비 후청구** — 같은 §5. `efs-billing` 재사용 불가
- **카페24 주문 상태 되돌려쓰기** — 출고했다고 카페24 에서 `배송중`으로 바꾸지 않는다. 송장 회신과 한 묶음이다
- **카페24 재고 동기화** — KLOW 창고 재고를 카페24 상품 재고에 반영하지 않는다. 축이 둘로 갈리면 어느 쪽이 정본인지 즉시 모호해진다
- **앱스토어(iframe) 진입** — 위 표 참고. 3rd-party 쿠키를 우회하는 별도 세션 수립이 필요하다

## 이 트랙이 `fulfillment` 모듈을 건드리는 두 곳

"EFS·`Shipment`·`Order` 를 안 건드린다"는 맞지만 **`fulfillment` 모듈은 두 군데 바뀐다.**
스펙은 [`implementation-plan.md`](./implementation-plan.md) §4-F·§7 R3 에 있다.

| 무엇 | 왜 |
|---|---|
| `FulfillmentRequest.source` 컬럼 추가 | 출고신청 목록에서 카페24 유입 건을 구별하는 유일하게 깨끗한 방법. 역조인으로 하면 브랜드·어드민·엑셀 세 곳이 같은 조인을 타야 한다 |
| 브랜드 목록에 `since`/`until` 서버 필터 | 지금은 200건을 받아 클라에서 기간 필터를 건다. 카페24 유입이 붙으면 **몇 주 만에 잘리고 기간 칩의 건수가 거짓말을 한다** |
