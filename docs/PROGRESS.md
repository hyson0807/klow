# KLOW 진행표

**이 문서 하나로 단계별 작업을 진행한다.** 사용자는 새 세션마다 아래 한 줄만 보낸다.

```
docs/PROGRESS.md 를 읽고 다음 단계를 진행해 줘.
```

한 세션은 **한 단계만** 한다. 단계를 끝내면 `§7 진행 기록` 과 `§0 지금 할 것` 을 고치고 인계 메모를
채운 뒤 커밋하고, 사용자에게 새 세션에서 위 한 줄을 다시 보내라고 안내하고 **멈춘다**. 다음 단계를
이어서 시작하지 않는다. 대화가 길어지면 품질이 떨어지기 때문이다.

**이 문서가 상태의 유일한 정본이다.** 트랙 문서(`docs/<트랙>/`)는 **스펙**을 갖고,
"지금 어디까지 왔나"와 "무엇이 참이어야 끝인가"는 여기 있다. 두 곳이 어긋나면 이 문서가 이긴다.

## 1. 세션 절차

1. **다음 단계 찾기** — `§0 지금 할 것` 의 첫 줄을 한다. 사용자가 다른 것을 지정했으면 그쪽을 한다.
   `§0` 이 비었거나 근거가 **2주 넘게 낡았으면 멈추고 사용자에게 우선순위를 묻는다** — 추측해서
   고르지 않는다.
2. **인계 메모 읽기** — `§9` 에서 같은 트랙의 직전 메모를 읽는다. 문서와 다르게 구현한 것, 확인하지
   못한 것이 거기 있다.
3. **"읽을 것"만 읽는다** — 그 단계가 지정한 것만. 전부 읽지 않는다. `CLAUDE.md` 는 자동 로드되므로
   따로 읽지 않는다. 단계가 지정한 `decisions/*.md` 만 더 읽는다.
4. **작업 레포로 `cd`** — 워크스페이스 루트에서 서브레포 파일을 절대 stage 하지 않는다.
5. **구현** — `§4 공통 규칙` 을 지킨다.
6. **검증** — `§4` 의 검증 3층 중 해당하는 것 + 그 단계 고유의 완료 기준.
7. **문서 동기화** — 컨트롤러가 바뀌었으면 `server/modules/<module>.md`(**필수**). 새 결정·함정이면
   `decisions/<주제>.md` 맨 뒤에 `<a id="<날짜>"></a>` + `## 제목 (날짜)` 로 항목을 더하고,
   **`decisions/README.md` 표와 `CLAUDE.md` 의 `## 결정 기록` 색인 두 곳에 한 줄씩** 넣는다.
   그 색인이 자동 로드되는 유일한 흔적이라 빠뜨리면 다음 세션이 그 결정을 모른다.
8. **기록** — `§7` 표 갱신 + `§9` 인계 메모(10줄 안쪽) + **`§0 지금 할 것` 갱신**.
   **표를 안 고쳤으면 커밋하지 않는다.**
9. **커밋** — 레포마다 따로 커밋한다. 메시지는 각 레포의 최근 커밋 관례를 따른다.
   **push 하지 않는다.**
10. **보고하고 멈춤** — 한 일 / 검증 결과 / 고친 문서 / 사용자가 할 일(있으면)을 알리고, 마지막 줄에
    재진입 한 줄을 안내한다.

### 새 계획을 추가할 때 — 계획 세션

사용자가 아래처럼 보내면 **계획만 하고 코드는 건드리지 않는다.**

```
docs/PROGRESS.md 를 읽고 <할 일>을 계획에 추가해 줘.
```

1. **진입 판정을 먼저 한다** — `§2 진입 기준` 에 하나도 안 걸리면 **트랙을 만들지 않는다.** "그냥
   지금 하면 되는 일"이라고 말하고 확인을 받은 뒤 바로 한다. 단계가 하나뿐인 계획은 표에 올릴
   이유가 없다.
2. **조사한다** — 건드릴 코드·문서를 훑어 전제를 확인한다. 모르는 채로 쪼갠 단계는 착수 즉시
   틀어진다.
3. **정책 공백은 묻는다** (`§3`). 추측해서 계획에 박지 않는다 — 계획서에 박힌 추측은 다음 세션이
   사실로 읽는다.
4. **단계로 쪼갠다** — 한 단계 = 한 세션. **레포 경계와 마이그레이션이 자연 분할선**이고 배포
   순서와도 일치한다. ⚠️ **마이그레이션은 항상 독립 단계로 뗀다** — 스키마 + 백필 + 코드 + 배포를
   한 세션에 넣으면 반드시 넘친다.
5. **첫 1~2단계만 `§5` 템플릿으로 정밀하게 쓴다.** 나머지는 제목과 순서만 남긴다. 뒤 단계의 전제는
   앞 단계가 끝나야 확정되므로, 미리 쓰면 착수 시점엔 틀려 있다 — **틀린 명세는 없는 명세보다
   나쁘다.**
6. **계획 문서는 `docs/plan/<트랙>/` 폴더 안에 쓴다** — 최상위에 평평하게 두지 않는다(트랙이 늘면
   최상위가 다시 뒤섞인다). `plan/custom-domain/`·`plan/mcf/` 가 선례이고 구성은 셋이다.

   | 파일 | 역할 |
   |---|---|
   | `README.md` | 결정 요약 · 읽는 순서 · 각 문서의 정본 범위 |
   | `flow.md` | 전체 흐름과 설계 논거 ("왜 이렇게 하나") |
   | `implementation-plan.md` | **정본 — 실제 빌드 스펙.** 단계별 명세와 착수 게이트(불변식) |

   작은 트랙이면 `implementation-plan.md` 하나로 시작해도 되지만 **폴더는 만든다** — 나중에
   쪼갤 때 링크가 안 깨진다. ⚠️ 어느 문서에도 **상태를 적지 않는다.** 상태는 `§7` 뿐이다.
   자세히는 [`plan/README.md`](./plan/README.md).
7. **기록** — `§6` 에 트랙 섹션(폴더 링크 + 다음 단계만) + `§7` 표 행 + `§0 지금 할 것` 갱신.
   `README.md` 문서 지도와 `plan/README.md` 에도 폴더를 등재한다. 커밋하고 push 하지 않는다.
8. **멈춘다.** 방금 계획한 단계를 이어서 실행하지 않는다 — **계획도 한 단계다.** 실행은 다음
   세션에서 재진입 한 줄로 시작한다.

### 사용자가 표에 없는 일을 바로 시켰을 때

**막지 않는다.** 진행표를 보지 않고 바로 한다. **끝날 때만** `§2 진입 기준` 에 걸리는지 판정해서,
걸리면 트랙·행을 만들고 아니면 모듈 문서와 커밋으로 닫는다. 진행표는 입구가 아니라 **출구**에서
작동한다.

⚠️ 그 요청이 `진행 중` 인 단계와 같은 파일을 건드리면 **먼저 경고한다** — 그 단계의 인계 메모가
무효화된다.

## 2. 진입 / 퇴출 기준

**진행표는 할 일 목록이 아니라 "세션 경계를 넘는 일"의 목록이다.** 한 세션에 시작해서 끝나는 일은
그 세션의 보고와 커밋이 곧 기록이고, 표에 들어오지 않는다.

### 진입 — 하나라도 해당하면 행이 된다

1. 2세션 이상 걸릴 것 같다
2. 레포 2개 이상을 **순서대로** 배포해야 한다
3. Prisma 마이그레이션을 동반한다
4. 외부 의존·승인 대기가 있다 (Eximbay·AWS 크레딧·Amazon Role·Vercel·카카오 검수)
5. **착수와 완료가 세션으로 끊긴다 — 스테이징 완료 후 운영 배포 대기 포함**

단일 레포 버그 수정·문구 변경·어드민 한 화면 수정은 아무리 급해도 표에 안 들어간다. 모듈 문서와
커밋 메시지가 이미 그 일을 하고 있고, 그걸 깨면 안 된다. 착수 결정이 안 난 백로그(예:
`brand-subscription.md` §11 의 미구현 4건)도 진입 기준 미달이다 — 착수하기로 하는 순간 행이 된다.

### 퇴출 — 시간이 아니라 사건으로

**`완료` + 운영 배포 확인 + 그 트랙의 다음 단계가 없거나 완료.** 완료 행은 `§8 최근 완료` 로 내리고,
상한(10행 또는 4주)을 넘으면 인계 메모와 함께 `archive/progress-2026-H2.md` 로 옮긴다.

⚠️ **회수 대상은 상태 행과 인계 메모이지 스펙이 아니다.** 완료 단계의 스펙은 트랙 문서에 원문 그대로
남는다.

**트랙 전체가 끝나면 그 폴더는 `plan/` 을 떠난다.** 판정 기준은 *"이 문서가 현행 동작의 유일한
설명인가"* 다.

- **유일한 설명이면 → `reference/`.** 계획 서술(단계·PR 분할·배포 순서)을 걷어내고 "지금 어떻게
  동작하나"만 남긴다
- **`server/modules/` 나 다른 reference 문서가 이미 그 역할을 하면 → `archive/`** + 📦 배너 +
  정본 포인터

⚠️ **정리하지 않은 계획서를 그대로 `reference/` 에 넣지 말 것** — "무엇을 만들 것인가"와 "무엇이
동작하는가"가 한 문서에 섞이고, 다음 사람이 계획 단계의 문장을 현행 사양으로 읽는다.

## 3. 멈추고 사용자에게 물어볼 때

- 마이그레이션이 필요한데 Neon DB 브랜치가 없을 때
- 문서에 없거나 미결정인 정책을 정해야 할 때. **추측해서 구현하지 않는다**
- 문서끼리 서로 달라서 어느 쪽이 맞는지 판단할 근거가 없을 때
- 프로덕션 DB·운영 배포·외부 벤더 콘솔에 손대야 할 때
- 단계가 너무 커서 한 세션에 끝낼 수 없을 때: 멈추지 말고 **일관된 단위까지 끝내고 커밋한 뒤**
  `진행 중(부분 완료)` 로 기록하고 남은 일을 인계 메모에 적는다

## 4. 공통 규칙

전 단계에 걸리는 klow 고유 제약. 정본은 `../CLAUDE.md` 이고 여기엔 **세션 절차상 언제 걸리는지**만
적는다.

- **레포 독립성** — 5개 서브레포는 각자 독립 git 레포다. 워크스페이스 루트에서 서브레포 파일을
  stage·commit 하지 않는다. 작업 전에 해당 디렉토리로 `cd`.
- **Prisma** — `npx prisma migrate dev --name <이름>` 만 쓴다(예외: 순수 rename). 스키마를 바꾸는
  작업은 **git 브랜치 + Neon DB 브랜치를 함께** 판다. 드리프트를 리셋으로 풀지 않는다 — 그 DB 의
  데이터가 전부 지워진다.
- **검증 3층** (klow_server 를 건드린 단계는 전부)
  1. `npm run typecheck` — tsconfig **2개**를 돈다. ⚠️ `npx tsc --noEmit` 만 쓰면 `src/` 밖(seed·
     backfill 스크립트)이 조용히 깨진다
  2. `npm run test:e2e` — 35개 모듈 DI 그래프 + **cron 개수**. 새 cron 을 추가하면 기대 목록도 고친다
  3. `npm run start` — env 가드 + 실 DB 접속 + 라우트 매핑 수(부팅 로그가 정본)
- **배포 순서** — 보통 `klow_server → klow_admin → klow_brand → klow_web`. 뒤집으면 400(구 zod 가
  새 필드 거부) · 404(라우트 없음) · **조용한 strip**(non-strict zod 가 새 필드를 버린다)이 난다.
  단계마다 순서와 "뒤집으면 뭐가 깨지는지"를 명시한다.
- **마이그레이션 롤링 안전성** — nullable `ADD COLUMN`·`CREATE TABLE` 은 안전. `DROP COLUMN`·
  `DROP TABLE`·enum 값 제거는 **단일 레플리카 컷오버**가 필요하다.
- **모듈 문서 갱신 계약** — 컨트롤러를 추가·변경하면 `server/modules/<module>.md` 를 함께 갱신한다.
  이건 선택이 아니라 완료 기준의 필수 항목이다.
- **WIP 상한** — 동시 `진행 중` 은 **2 트랙**까지, **마이그레이션을 동반하는 단계는 동시에 1개**까지.
  같은 파일을 반쯤 고친 단계가 둘이면 인계 메모가 서로를 무효화한다.
- **상설 환경 변수 표를 만들지 않는다** — 5개 레포의 `.env.example` 이 정본이다. 여기 복사하면
  드리프트 지점이 하나 더 생긴다. env 를 실제로 추가하는 단계에서는 그 단계의 `할 일`·`완료 기준`
  안의 한 줄로 적는다.

```markdown
#### N. <단계 이름>

- **읽을 것**: <섹션 단위로. 전부 읽지 않는다>
- **건드리는 레포 · 배포 순서**: klow_server → klow_admin (뒤집으면 …) / 또는 `배포 없음`
- **스키마·데이터 위험**: 없음 / <마이그레이션명> · 롤링 안전 여부 · 백필 · DB 브랜치 필요 여부
- **할 일**: <레포별로 묶어서>
- **완료 기준**: <이 단계 고유의 확인만. 공통 3층은 §4 에 한 번>
- **(해당 시) 불변식**: custom-domain §9 F21·F30  ← 번호만. 전문 복사 금지
- **(선택) 선행 조건 / 시점**
```

필드 규칙:

- **읽을 것** — 이 체계의 유일한 컨텍스트 통제 장치다. 파일이 아니라 **섹션**으로 지정한다
  (`purchase-plan.md §12~§15`). 건드리는 모듈의 `server/modules/<m>.md` 와 필요한
  `decisions/<주제>.md` 만 적는다.
- **스키마·데이터 위험** — 없으면 **`없음` 이라고 명시적으로 쓴다.** 빈칸은 "생각 안 함"과 구분이
  안 된다.
- **할 일** — 한 세션에서 끝낼 분량. 길어지면 `2-1`, `2-2` 로 쪼개 별도 세션으로 강제한다.
- **완료 기준** — 그 단계 **고유의** 확인만. 실행 가능한 형태(명령·curl·화면)로 쓴다.

트랙이 이미 상세 계획서를 가졌으면 여기엔 **읽을 것 + 완료 기준만** 쓰고 본문은 트랙 문서로 링크한다.
같은 내용을 두 곳에 쓰지 않는다.
