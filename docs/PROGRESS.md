# KLOW 진행표

**이 문서 하나로 단계별 작업을 진행한다.** 사용자는 새 세션마다 아래 한 줄만 보낸다.

```
docs/PROGRESS.md 를 읽고 다음 단계를 진행해 줘.
```

한 세션은 **한 단계만** 한다. 단계를 끝내면 `§7 진행 기록` 과 `§0 지금 할 것` 을 고치고 인계 메모를
채운 뒤 커밋하고, 사용자에게 새 세션에서 위 한 줄을 다시 보내라고 안내하고 **멈춘다**. 다음 단계를
이어서 시작하지 않는다. 대화가 길어지면 품질이 떨어지기 때문이다.

⚠️ **예외 — `§7` 1·2·3행(b2bpc 이식 3트랙)은 트랙 하나를 한 세션에 끝낸다.**
그 세 행에서는 `§0` 이 가리키는 단위가 단계가 아니라 **트랙 전체**이고, 트랙 안의 단계는 세션 안의
순서이자 넘칠 때의 정지점이다(`§6 의 한 트랙 = 한 세션` 이 정본).
**그렇게 지정되지 않은 행은 위 원칙 그대로 한 단계만 한다** — 스스로 묶지 않는다.

**이 문서가 상태의 유일한 정본이다.** 트랙 문서(`docs/<트랙>/`)는 **스펙**을 갖고,
"지금 어디까지 왔나"와 "무엇이 참이어야 끝인가"는 여기 있다. 두 곳이 어긋나면 이 문서가 이긴다.

## 1. 세션 절차

1. **다음 단계 찾기** — `§0 지금 할 것` 의 첫 줄을 한다. 사용자가 다른 것을 지정했으면 그쪽을 한다.
   `§0` 이 비었거나 근거가 **2주 넘게 낡았으면 멈추고 사용자에게 우선순위를 묻는다** — 추측해서
   고르지 않는다.
2. **인계 메모 읽기** — `§9` 에서 같은 트랙의 직전 메모를 읽는다. 문서와 다르게 구현한 것, 확인하지
   못한 것이 거기 있다.
3. **"읽을 것"만 읽는다** — 그 단계가 지정한 것만. 전부 읽지 않는다. `CLAUDE.md` 는 자동 로드되므로
   따로 읽지 않는다. 단계가 지정한 `decisions/*.md` 만 더 읽는다.
4. **작업 레포로 `cd`** — 워크스페이스 루트에서 서브레포 파일을 절대 stage 하지 않는다.
5. **구현** — `§4 공통 규칙` 을 지킨다.
6. **검증** — `§4` 의 검증 3층 중 해당하는 것 + 그 단계 고유의 완료 기준.
7. **문서 동기화** — 컨트롤러가 바뀌었으면 `server/modules/<module>.md`(**필수**). 새 결정·함정이면
   `decisions/<주제>.md` 맨 뒤에 `<a id="<날짜>"></a>` + `## 제목 (날짜)` 로 항목을 더하고,
   **`decisions/README.md` 표와 `CLAUDE.md` 의 `## 결정 기록` 색인 두 곳에 한 줄씩** 넣는다.
   그 색인이 자동 로드되는 유일한 흔적이라 빠뜨리면 다음 세션이 그 결정을 모른다.
8. **기록** — `§7` 표 갱신 + `§9` 인계 메모(10줄 안쪽) + **`§0 지금 할 것` 갱신**.
   **표를 안 고쳤으면 커밋하지 않는다.**
9. **커밋** — 레포마다 따로 커밋한다. 메시지는 각 레포의 최근 커밋 관례를 따른다.
   **push 하지 않는다.**
10. **보고하고 멈춤** — 한 일 / 검증 결과 / 고친 문서 / 사용자가 할 일(있으면)을 알리고, 마지막 줄에
    재진입 한 줄을 안내한다.

### 새 계획을 추가할 때 — 계획 세션

사용자가 아래처럼 보내면 **계획만 하고 코드는 건드리지 않는다.**

```
docs/PROGRESS.md 를 읽고 <할 일>을 계획에 추가해 줘.
```

1. **진입 판정을 먼저 한다** — `§2 진입 기준` 에 하나도 안 걸리면 **트랙을 만들지 않는다.** "그냥
   지금 하면 되는 일"이라고 말하고 확인을 받은 뒤 바로 한다. 단계가 하나뿐인 계획은 표에 올릴
   이유가 없다.
2. **조사한다** — 건드릴 코드·문서를 훑어 전제를 확인한다. 모르는 채로 쪼갠 단계는 착수 즉시
   틀어진다.
3. **정책 공백은 묻는다** (`§3`). 추측해서 계획에 박지 않는다 — 계획서에 박힌 추측은 다음 세션이
   사실로 읽는다.
4. **단계로 쪼갠다 — ⚠️⚠️ 한 계획이 `§7` 에 더하는 행은 최대 3개다** (2026-09-29 사용자 결정).
   한 단계 = 한 세션. **레포 경계와 마이그레이션이 자연 분할선**이고 배포 순서와도 일치한다.
   ⚠️ **마이그레이션은 항상 독립 단계로 뗀다** — 스키마 + 백필 + 코드 + 배포를 한 세션에 넣으면
   반드시 넘친다.

   **3개에 안 들어가면 쪼개지 말고 묶는다.** 한 계획이 표를 5~6행씩 늘리면 `§7` 이 "지금 무엇을
   하나"가 아니라 "언젠가 할 일 목록"이 되고, 그 순간 이 문서의 목적이 사라진다. 묶는 순서는 이렇다.

   | 순서 | 어떻게 |
   |---|---|
   | 1 | **레포를 묶는다** — 배포 순서가 인접하고 한쪽이 다른 쪽의 전제면 한 행으로 (`server → admin`) |
   | 2 | **마무리를 마지막 행에 얹는다** — 문서·주석 정정, 운영 배포는 독립 행이 될 만큼 크지 않다 |
   | 3 | **행 안에 `세션 안 순서`를 적는다** — 그게 곧 **넘칠 때의 정지점**이다. 넘치면 거기서 끊고 `진행 중(부분 완료)` 로 기록한다(`§3`) |
   | 4 | 그래도 안 되면 **범위를 줄이거나 트랙을 둘로 나눈다** — 두 번째 트랙은 지금 표에 올리지 않는다 |

   ⚠️ **3은 목표이지 보장이 아니다.** 한 행이 두 세션이 되는 것은 정상이고(`§6` b2bpc 3트랙 선례),
   그건 표를 늘리지 않은 채 인계 메모로 흡수된다.
5. **첫 1~2단계만 `§5` 템플릿으로 정밀하게 쓴다.** 나머지는 제목과 순서만 남긴다. 뒤 단계의 전제는
   앞 단계가 끝나야 확정되므로, 미리 쓰면 착수 시점엔 틀려 있다 — **틀린 명세는 없는 명세보다
   나쁘다.**
6. **계획 문서는 `docs/plan/<트랙>/` 폴더 안에 쓴다** — 최상위에 평평하게 두지 않는다(트랙이 늘면
   최상위가 다시 뒤섞인다). `plan/custom-domain/`·`plan/mcf/` 가 선례이고 구성은 셋이다.

   | 파일 | 역할 |
   |---|---|
   | `README.md` | 결정 요약 · 읽는 순서 · 각 문서의 정본 범위 |
   | `flow.md` | 전체 흐름과 설계 논거 ("왜 이렇게 하나") |
   | `implementation-plan.md` | **정본 — 실제 빌드 스펙.** 단계별 명세와 착수 게이트(불변식) |

   작은 트랙이면 `implementation-plan.md` 하나로 시작해도 되지만 **폴더는 만든다** — 나중에
   쪼갤 때 링크가 안 깨진다. ⚠️ 어느 문서에도 **상태를 적지 않는다.** 상태는 `§7` 뿐이다.
   자세히는 [`plan/README.md`](./plan/README.md).
7. **기록** — `§6` 에 트랙 섹션(폴더 링크 + 다음 단계만) + `§7` 표 행 + `§0 지금 할 것` 갱신.
   `README.md` 문서 지도와 `plan/README.md` 에도 폴더를 등재한다. 커밋하고 push 하지 않는다.
8. **멈춘다.** 방금 계획한 단계를 이어서 실행하지 않는다 — **계획도 한 단계다.** 실행은 다음
   세션에서 재진입 한 줄로 시작한다.

### 사용자가 표에 없는 일을 바로 시켰을 때

**막지 않는다.** 진행표를 보지 않고 바로 한다. **끝날 때만** `§2 진입 기준` 에 걸리는지 판정해서,
걸리면 트랙·행을 만들고 아니면 모듈 문서와 커밋으로 닫는다. 진행표는 입구가 아니라 **출구**에서
작동한다.

⚠️ 그 요청이 `진행 중` 인 단계와 같은 파일을 건드리면 **먼저 경고한다** — 그 단계의 인계 메모가
무효화된다.

## 2. 진입 / 퇴출 기준

**진행표는 할 일 목록이 아니라 "세션 경계를 넘는 일"의 목록이다.** 한 세션에 시작해서 끝나는 일은
그 세션의 보고와 커밋이 곧 기록이고, 표에 들어오지 않는다.

### 진입 — 하나라도 해당하면 행이 된다

1. 2세션 이상 걸릴 것 같다
2. 레포 2개 이상을 **순서대로** 배포해야 한다
3. Prisma 마이그레이션을 동반한다
4. 외부 의존·승인 대기가 있다 (Eximbay·AWS 크레딧·Amazon Role·Vercel·카카오 검수)
5. **착수와 완료가 세션으로 끊긴다 — 스테이징 완료 후 운영 배포 대기 포함**

단일 레포 버그 수정·문구 변경·어드민 한 화면 수정은 아무리 급해도 표에 안 들어간다. 모듈 문서와
커밋 메시지가 이미 그 일을 하고 있고, 그걸 깨면 안 된다. 착수 결정이 안 난 백로그(예:
`brand-subscription.md` §11 의 미구현 4건)도 진입 기준 미달이다 — 착수하기로 하는 순간 행이 된다.

### 퇴출 — 시간이 아니라 사건으로

**`완료` + 운영 배포 확인 + 그 트랙의 다음 단계가 없거나 완료.** 완료 행은 `§8 최근 완료` 로 내리고,
상한(10행 또는 4주)을 넘으면 인계 메모와 함께 `archive/progress-2026-H2.md` 로 옮긴다.

⚠️ **회수 대상은 상태 행과 인계 메모이지 스펙이 아니다.** 완료 단계의 스펙은 트랙 문서에 원문 그대로
남는다.

**트랙 전체가 끝나면 그 폴더는 `plan/` 을 떠난다.** 판정 기준은 *"이 문서가 현행 동작의 유일한
설명인가"* 다.

- **유일한 설명이면 → `reference/`.** 계획 서술(단계·PR 분할·배포 순서)을 걷어내고 "지금 어떻게
  동작하나"만 남긴다
- **`server/modules/` 나 다른 reference 문서가 이미 그 역할을 하면 → `archive/`** + 📦 배너 +
  정본 포인터

⚠️ **정리하지 않은 계획서를 그대로 `reference/` 에 넣지 말 것** — "무엇을 만들 것인가"와 "무엇이
동작하는가"가 한 문서에 섞이고, 다음 사람이 계획 단계의 문장을 현행 사양으로 읽는다.

## 4. 공통 규칙

전 단계에 걸리는 klow 고유 제약. 정본은 `../CLAUDE.md` 이고 여기엔 **세션 절차상 언제 걸리는지**만
적는다.

- **레포 독립성** — 5개 서브레포는 각자 독립 git 레포다. 워크스페이스 루트에서 서브레포 파일을
  stage·commit 하지 않는다. 작업 전에 해당 디렉토리로 `cd`.
- **Prisma** — `npx prisma migrate dev --name <이름>` 만 쓴다(예외: 순수 rename). 스키마를 바꾸는
  작업은 **git 브랜치 + Neon DB 브랜치를 함께** 판다. 드리프트를 리셋으로 풀지 않는다 — 그 DB 의
  데이터가 전부 지워진다.
- **검증 3층** (klow_server 를 건드린 단계는 전부)
  1. `npm run typecheck` — tsconfig **2개**를 돈다. ⚠️ `npx tsc --noEmit` 만 쓰면 `src/` 밖(seed·
     backfill 스크립트)이 조용히 깨진다
  2. `npm run test:e2e` — 35개 모듈 DI 그래프 + **cron 개수**. 새 cron 을 추가하면 기대 목록도 고친다
  3. `npm run start` — env 가드 + 실 DB 접속 + 라우트 매핑 수(부팅 로그가 정본)
- **배포 순서** — 보통 `klow_server → klow_admin → klow_brand → klow_web`. 뒤집으면 400(구 zod 가
  새 필드 거부) · 404(라우트 없음) · **조용한 strip**(non-strict zod 가 새 필드를 버린다)이 난다.
  단계마다 순서와 "뒤집으면 뭐가 깨지는지"를 명시한다.
- **마이그레이션 롤링 안전성** — nullable `ADD COLUMN`·`CREATE TABLE` 은 안전. `DROP COLUMN`·
  `DROP TABLE`·enum 값 제거는 **단일 레플리카 컷오버**가 필요하다.
- **모듈 문서 갱신 계약** — 컨트롤러를 추가·변경하면 `server/modules/<module>.md` 를 함께 갱신한다.
  이건 선택이 아니라 완료 기준의 필수 항목이다.
- **WIP 상한** — 동시 `진행 중` 은 **2 트랙**까지, **마이그레이션을 동반하는 단계는 동시에 1개**까지.
  같은 파일을 반쯤 고친 단계가 둘이면 인계 메모가 서로를 무효화한다.
- **상설 환경 변수 표를 만들지 않는다** — 5개 레포의 `.env.example` 이 정본이다. 여기 복사하면
  드리프트 지점이 하나 더 생긴다. env 를 실제로 추가하는 단계에서는 그 단계의 `할 일`·`완료 기준`
  안의 한 줄로 적는다.

## 5. 단계 명세 템플릿

```markdown
#### N. <단계 이름>

- **읽을 것**: <섹션 단위로. 전부 읽지 않는다>
- **건드리는 레포 · 배포 순서**: klow_server → klow_admin (뒤집으면 …) / 또는 `배포 없음`
- **스키마·데이터 위험**: 없음 / <마이그레이션명> · 롤링 안전 여부 · 백필 · DB 브랜치 필요 여부
- **할 일**: <레포별로 묶어서>
- **완료 기준**: <이 단계 고유의 확인만. 공통 3층은 §4 에 한 번>
- **(해당 시) 불변식**: custom-domain §9 F21·F30  ← 번호만. 전문 복사 금지
- **(선택) 선행 조건 / 시점**
```

필드 규칙:

- **읽을 것** — 이 체계의 유일한 컨텍스트 통제 장치다. 파일이 아니라 **섹션**으로 지정한다
  (`purchase-plan.md §12~§15`). 건드리는 모듈의 `server/modules/<m>.md` 와 필요한
  `decisions/<주제>.md` 만 적는다.
- **스키마·데이터 위험** — 없으면 **`없음` 이라고 명시적으로 쓴다.** 빈칸은 "생각 안 함"과 구분이
  안 된다.
- **할 일** — 한 세션에서 끝낼 분량. 길어지면 `2-1`, `2-2` 로 쪼개 별도 세션으로 강제한다.
- **완료 기준** — 그 단계 **고유의** 확인만. 실행 가능한 형태(명령·curl·화면)로 쓴다.

트랙이 이미 상세 계획서를 가졌으면 여기엔 **읽을 것 + 완료 기준만** 쓰고 본문은 트랙 문서로 링크한다.
같은 내용을 두 곳에 쓰지 않는다.

다시 썼다. ⚠️ 그러나 **계획 문서·결정 로그는 아직 이 트랙을 "해외배송 출고" 축으로 서술**한다 —
정리 여부는 미결이다.

⚠️ **앱 이름과 판매 상품명이 엇갈려 있다** — 개발자센터 앱 이름은 `KLOW 해외배송 출고연동`,
스토어 판매 상품명은 `KLOW 풀필먼트 출고연동`. **앱 이름은 개발자센터 UI 에 수정 경로가 없다**
(`app_name` 이 hidden 필드로만 있고, 그걸 고쳐 저장하면 **Redirect URI·App URL 이 같이 제출돼
OAuth 설정이 깨질 위험**이 있다). 2026-09-23 사용자 결정: **그대로 두고 8단계 제출 전에
카페24에 변경 요청**한다. 브랜드가 보는 **동의 화면에는 옛 이름이 뜬다**는 것을 알고 간다.

⚠️ **테스트 몰 `simsgood1` 은 양쪽 다 해제했다**(2026-09-23) — 카페24 쪽 앱 삭제 + 우리 쪽
`disconnect()`. **배포 확인 때 카페24 왕복을 돌리려면 재연동부터** 해야 한다(HTTPS 터널 →
개발자센터 Redirect URI 추가 → 동의 1회). ⚠️ 운영 배포 뒤라면 터널 없이 운영 주소로 바로 된다.

⚠️ **심사 전 설치 한도 5개가 "테스트 설치까지 세는지" 미확인이다.** 카페24 한도는 앱
(`client_id`) 단위인데 dev·운영이 같은 앱을 쓰고, 우리 가드
(`CAFE24_MAX_BETA_CONNECTIONS`)는 **그 DB 의 행 수**를 세므로 두 카운트가 어긋날 수 있다.
→ **7단계 시범을 4곳까지만 잡으면** 이 불확실성을 피한다. 5곳이 필요해지는 시점이면
이미 심사를 낼 때다.

#### staging 에서 카페24 왕복을 돌린다 — 필요한 값

✅ **라우트는 이미 떴다**(위 실측 — `/v1/brand/cafe24/callback` 404 → **302**). 아래 표는 이제
**env·개발자센터 설정 점검표**다.

⚠️ **1~6 중 무엇이 실제로 설정됐는지는 확인하지 못했다** — 라우트가 응답하는 것은 코드가 배포됐다는
뜻이고 `CAFE24_CLIENT_ID` 류가 채워졌다는 뜻이 아니다. **왕복을 돌리기 전에 한 줄씩 확인할 것.**

| # | 할 일 | 값 |
|---|---|---|
| 1 | ~~개발자센터 STEP 01 **Redirect URI 한 줄 추가**~~ | ✅ **이미 등록돼 있었다**(2026-09-29 확인) — `https://api-staging.klow.kr/v1/brand/cafe24/callback` |
| 2 | staging 서버 env | `CAFE24_CLIENT_ID` · `CAFE24_CLIENT_SECRET`(운영과 **같은 앱**) |
| 3 | staging 서버 env | `CAFE24_BRAND_CALLBACK_URL` = 위 1번 주소 (**운영과 다른 값**) |
| 4 | staging 서버 env | `CAFE24_TOKEN_ENCRYPTION_KEY` — ⚠️ **운영과 다른 키를 쓴다**(DB 가 다르고, 키를 나눠야 한쪽 유출·회전이 다른 쪽을 죽이지 않는다) |
| 5 | staging 서버 env 확인 | `BRAND_FRONTEND_URL` = `https://brand-staging.klow.kr` (콜백 후 돌아갈 곳) |
| 6 | staging DB | 마이그레이션 **2개를 순서대로** |

⚠️⚠️ **5개 몰 한도는 staging·운영이 같이 쓸 수 있다** — 한도가 앱(`client_id`) 단위인데 두 환경이
같은 앱을 쓴다. 그래서 staging 테스트로 붙인 몰이 운영에서 쓸 자리를 먹을 **가능성**이 있다.

⚠️ **그렇다고 테스트가 끝날 때마다 지울 일은 아니다**(2026-09-29 판단 정정). 근거가 둘 다 약하다 —
① **합산되는지 자체가 미확인**이고(위 "심사 전 설치 한도 5개가 …" 절), ② 지금 붙은 몰은 `simsgood1` **1개**뿐이라
7단계 시범 1~2곳을 더해도 **3 < 5** 로 여유가 있다. 지우면 재연동 때 OAuth 동의를 다시 받아야 하므로
오히려 손해다. 개발자센터 대시보드의 `설치 수` 는 **0** 으로 나오는데, 그게 "한도에도 안 잡힌다"는
뜻인지는 **확인하지 못했다**.

→ **지울 시점은 둘 중 하나다**: ① 운영에서 실브랜드를 붙이는데 **5자리가 실제로 모자랄 때**,
② **심사 제출 직전**(심사자가 설치 목록을 본다면 테스트 몰이 섞여 있지 않은 편이 낫다).
방치해도 `연동 관리` 의 **재연동까지 14일**이 지나면 끊긴다.

⚠️ `CAFE24_BRAND_CALLBACK_URL` 은 서버당 env 하나라 staging·운영이 각자 제 주소를 가리키면
충돌하지 않는다. ⚠️ **`/connect` 와 `/callback` 은 반드시 같은 오리진**이어야 한다 —
`/connect` 가 심는 쿠키 4종(state·brand·returnTo·mallId)이 그 도메인에 붙기 때문이다
(로컬에서 시작해 운영으로 돌아오면 `state_mismatch`·`missing_brand` 로 떨어진다).

⚠️⚠️ **심사는 staging 주소로 내지 않는다**(2026-09-23 결정). App URL 은 심사 통과 후 **실제
브랜드가 들어가는 주소**가 되고, staging 은 배포마다 끊기고 데이터도 리셋 대상이다.
그리고 **심사 통과 후 App URL·Redirect URI 를 바꾸면 재심사가 필요한지 미확인**이라,
staging 으로 받은 심사가 통째로 무의미해질 수 있다 — **카페24에 문의해 확인할 값**이다.
심사를 서두를 이유도 없다: **심사 없이도 5개 몰이 붙으므로 7단계 시범은 운영에서 그대로 돈다.**

- ⚠️ **`feat/3pl-fulfillment` 는 `staging` 에 머지됐다**(2026-09-28). 남은 작업은 `staging`
  에서 하고, 새 DB·git 브랜치를 파지 않는다. ⚠️ b2bpc 이식 트랙은 **별도 브랜치
  `feat/storefront-b2b`** 다 — 여기에 섞지 않는다.
- 7단계(실브랜드 시범)·8단계(심사 제출)는 그 뒤다.

3pl 트랙 문서 §5 의 나머지 후보(유럽 라우팅 · 내부 주문 자동 유입 · 물류비 후청구 · 배송 추적)는
그대로 백로그다. 착수 결정이 나면 `§1 계획 세션` 으로 행을 만든다.

### brand-menu-schema — 브랜드관 메뉴·PC 설정 정규화

스펙: [`plan/brand-menu-schema/`](./plan/brand-menu-schema/README.md) — 결정 요약은 `README.md`,
**빌드 스펙 정본은 `implementation-plan.md`** 의 1~4단계.

`klow_brand` 의 `b2bpc` 브랜치가 목업으로 만든 **메뉴 서랍(☰)** 과 **PC 설정 3개**를 서버에 얹는다.
지금 그 값들은 서버 `BrandStorySchema` 가 `.strict()` 없는 `z.object` 라 **400 없이 조용히 버려지고**
`localStorage['klow.brand.menu.v1']` 에만 산다.

⚠️⚠️ **이 트랙이 나머지 둘(`storefront-menu-pc` · `b2b-wholesale`)의 게이트다.** 특히 후자는
바이어 메뉴가 이 트랙의 메뉴를 물려받으므로 직접적이다.

⚠️ **Json 에 더 쌓지 않고 정규화한다**(2026-09-28 사용자 결정) — 테이블 3벌
(`BrandMenuItem`·`BrandPage`·`BrandPageChapter`) + `Brand` 스칼라 3개(PC). 근거는 ① `BrandTranslation`
이 스칼라 컬럼 모델이라 Json 배열을 번역할 수 없고(공지 팝업이 테이블을 고른 바로 그 이유), ② `story`
한 칸의 400 이 색·폰트·링크 저장까지 죽이는 함정이 `8줄 × 12챕터` 로 커지기 때문이다.

⚠️ **정규화가 회귀 하나를 데이터에서 없앤다** — b2bpc 의 손님측 필터는 스토리 줄에 `enabled` 만 보고
`&& !empty` 가드가 빠져 있어, 그대로 내면 **스토리를 만든 적 없는 브랜드 최대 41곳이 빈 페이지로 가는
"Brand Story" 줄을 얻는다.** 스토리를 보통 메뉴 행으로 만들고 **내용이 있는 브랜드에만** 백필하면
행이 없어 줄이 없다. 프론트 가드가 필요 없어진다.

⚠️ `Brand.story` Json 은 **드롭하지 않고 dormant 로 남긴다**(DROP 은 롤링 비안전 + 백필 롤백 여지).
그래서 **이행 어댑터**가 필요하다 — 배포 창의 구 프론트가 보내는 legacy `story` 를 서버가 테이블로
번역한다. Json 컬럼에는 더 이상 쓰지 않는다(정본이 둘이 되면 안 된다).

#### 완료 (2026-09-28 · `§7` 1행) — 4단계 전부

머지·정합 → 스키마·마이그레이션·백필 → 서버 API(+이행 어댑터) → klow_brand 재배선.
현행 사양의 정본은 [`server/modules/brands.md`](./server/modules/brands.md) 의
`brand-menu.controller.ts` 절 + [`brand-applications.md`](./server/modules/brand-applications.md) 의
이행 어댑터 절이고, 결정과 함정은
[`decisions/storefront.md` 2026-09-28](./decisions/storefront.md#2026-09-28) 에 올렸다.

⚠️ **운영 배포는 `✗` 로 남는다** — `§0` 의 "운영 배포는 한 줄로 묶여 있다" 참고. 그 배포에
**백필 `npm run backfill:brand-menu -- --apply`** 가 따라간다.

⚠️ 이 폴더의 `plan/` 퇴출(`§2`)은 운영 배포가 확인돼야 성립한다. 판정은 이미 났다 —
`server/modules/` 가 엔드포인트를 갖게 됐으므로 **`archive/`** 다.

### b2bpc 이식 3트랙 — **한 트랙 = 한 세션** · 정본

`§7` 1·2·3행은 **각 행이 대화 세션 하나**다(2026-09-28 사용자 결정). 트랙 안의 단계는 **그 세션
안에서 지키는 순서이자 넘칠 때의 정지점**이고, 세션을 나누는 선이 아니다. 세부 명세는 트랙 문서가 갖는다.

| `§7` | 세션 | 안에서 하는 순서 | 레포 · 배포 | 크기 |
|---|---|---|---|---|
| **1** | 브랜드관 메뉴·PC **서버화** | 머지·정합 → 스키마·마이그레이션·백필 → 서버 API → klow_brand 재배선 | brand → server → brand | 큼 |
| **2** | **손님 화면** (klow_web) | 메뉴 서랍 → PC 브랜드관 → PC 제품상세 → 운영 배포 | web | 중간 |
| **3** | **B2B 도매** 전체 | 스키마 → 서버 브랜드API·PDF → **AI 도매표 추출** → 공개API·주문·메일 → 대시보드 → 바이어 페이지 → 배포 | server → brand → web | ⚠️ **가장 큼** |

⚠️ **이것은 이 문서 머리의 "한 세션은 한 단계만 한다"를 이 세 행에 한해 덮는다.** 근거는 관례다 —
archive 에 `cafe24 4-1·4-2·5-2·5-3 (한 세션에 넷)` · `3pl 3~6단계 (한 세션에)` 가 있다.

#### 세션 안에서 지키는 규칙 넷

1. ⚠️⚠️ **마이그레이션을 먼저 치운다.** 1행은 머지→스키마 순, 3행은 스키마가 첫 순서다.
   넘쳐도 **스키마가 끝난 깨끗한 지점**에서 멈출 수 있다. 뒤로 미루면 스키마 없는 코드가 남는다.
2. ⚠️ **1행과 3행을 같은 세션에 넣지 않는다** — 둘 다 마이그레이션을 갖는다
   (`§4` 의 "마이그레이션 동반 단계는 동시에 1개").
3. **넘치면 트랙 문서의 단계 경계에서 끊는다.** 그 행을 `진행 중(부분 완료)` 로 바꾸고 **어느
   단계까지 했는지**를 인계 메모에 적는다. 다음 세션이 그 행을 이어서 집는다.
   ⚠️ **그래서 세션이 3번을 넘을 수 있다** — 3은 목표이지 보장이 아니다.
4. **한 세션 = 한 행.** 1행이 끝나기 전에 2행을 시작하지 않는다(`§4` WIP 상한).

⚠️ **3행이 가장 위험하다**(테이블 6벌 + 컨트롤러 3벌 + **AI 추출** + 3레포 화면). 끊기면
`서버까지`(스키마·API·AI·공개API) / `화면부터`(대시보드·바이어·배포) 경계가 자연스럽다 — 그 선이
배포 경계와도 같다. ⚠️ **AI 추출이 이 세션의 가장 무거운 조각**이다.
