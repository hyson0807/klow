# 브랜드 커스텀 도메인 연결 문서

KLOW 입점 브랜드가 자기 도메인(예: `shop.brandA.com`)을 연결하면, **그 주소에서 KLOW 쇼핑 흐름
전체**(브랜드관 → 제품 상세 → 장바구니 → 로그인 → 결제)가 동작하게 하는 기능의 설계 문서 모음.

> **현재 상태: 📄 문서 = 구현 미착수.** 5개 레포 어디에도 `customDomain` / `custom_domain` 문자열이
> **0건**이고, `klow_web` 에는 `src/middleware.ts` 자체가 없다. 완전한 신규 기능이다.
>
> 설계·통합 지점은 실측 코드와 대조해 확정했다 → 이 문서만 보고 구현에 들어갈 수 있다.
> ⚠️ **2026-08-20 설계 변경** — 결제·로그인을 `klow.kr` 로 넘기는 **핸드오프**로 바꿨다(원안은 결제까지
> 커스텀 도메인에서 끝내는 same-origin 프록시). 프록시·쿠키 전환·구글 핸드오프가 **전부 빠지고**,
> **🔴 #0(Eximbay)도 P3 전제에서 빠진다**(결제창 호출 도메인이 오늘과 같은 klow.kr). 원안은 폐기가
> 아니라 [P5 승격 경로](./implementation-plan.md#6-1-풀-프록시-승격--로그인결제까지-커스텀-도메인)로
> 보존한다 — **그때는 #0 회신이 선행 조건**이다.
>
> ⚠️ **`file:line` 은 2026-08-19 스냅샷**이다. 구현 시점엔 밀려 있을 수 있으니 **심볼명(함수/상수)으로
> 재확인**한 뒤 편집할 것.

## 목표 동작 (한 줄)

브랜드가 설정에서 도메인을 입력 → 안내된 DNS 레코드를 등록 → 몇 분 뒤 **그 도메인이 곧 브랜드의 KLOW
스토어**가 된다. 기존 `klow.kr/{slug}` 는 **그대로 살아있다**(301 하지 않는다).

## 다른 플랫폼은 어떻게 하나

두 곳 모두 방식이 같고, 핵심은 **"커스텀 도메인이 그 몰의 오리진 전부"** 라는 점이다.

| | 도메인 연결 | SSL | 몰 식별 | 세션·API |
|---|---|---|---|---|
| **카페24** | 브랜드가 등록기관(가비아 등)에서 **네임서버를 카페24로 변경**하거나 A레코드를 카페24 IP로 | 카페24가 무료 SSL 자동 발급 | 요청 **Host 헤더** → mall_id | 프론트·API·결제 전부 **그 도메인 한 곳**. 쿠키가 자기 도메인 쿠키라 3rd-party 이슈가 없다 |
| **쇼피파이** | 브랜드가 `CNAME → shops.myshopify.com` | Let's Encrypt 자동 | Host 헤더 → shop | 동일. 체크아웃도 같은 도메인 |
| **KLOW(이 설계)** | Vercel Domains API 자동 등록 + 안내된 A/CNAME | Vercel 자동 | Host → `BrandDomain.host` → slug | **둘러보기·담기만** 그 도메인. 결제·로그인은 `klow.kr` 로 핸드오프 → 쿠키·PG 전제가 오늘과 동일 |

## 확정된 핵심 결정

| 항목 | 결정 | 이유 |
|---|---|---|
| **API 접근 방식** | **프록시 없음.** 커스텀 도메인도 `api.klow.kr` 직행이되 **쿠키를 싣지 않는다**(`credentials:'omit'`) | 세션을 쓰지 않으므로 ITP·쿠키 문제가 성립하지 않는다. 남는 건 트래킹 비콘 2개의 Origin·CORS 뿐이고 그건 **서버 술어 하나로** 열린다 |
| **결제·로그인 경계** | **핸드오프** — 커스텀 도메인의 "결제하기"가 `klow.kr/handoff?h=…` 로 top-level 이동 | 결제창 호출 도메인이 오늘과 같은 `klow.kr` 이라 **PG 전제가 안 바뀐다.** 이음매도 원래 로그인을 묻는 지점과 겹친다(`useCheckoutGate`) |
| **핸드오프 payload** | 상태 4개(카트 id·수량 · 국가 · `promotionCode` · `visitorId`) + **복귀 host** 1개. **서명 없음**, **가격 없음** | 상태 4개는 이미 손님이 조작 가능하고 금액 정본은 서버다 → 서명은 지키는 게 0. ⚠️ **가격을 실으면 그 순간 서명이 필요해진다.** ⚠️ 복귀 host 만은 **링크로 렌더**되므로 서버 재검증(F21) |
| **결제 후 브랜드 도메인 카트** | 성공 화면 "계속 쇼핑" 링크에 `?purchased=` 를 실어 정리. **best-effort** | 기존 `brandReturn`·`checkoutSelection`·`removeProducts` 를 잇기만 한다(새 엔드포인트·토큰 0). iframe 정리는 **storage partitioning 때문에 원천적으로 불가** → [plan §3-4](./implementation-plan.md#3-4-결제-후-브랜드-도메인-카트-정리) |
| **데이터 모델** | `Brand` 컬럼이 아니라 **별도 `BrandDomain` 테이블** | apex 와 `www` 는 Vercel 에 각각 등록해야 하는 별개 도메인이고(레코드 타입도 A vs CNAME), 검증 상태 머신과 Vercel 챌린지 원문을 담을 곳이 필요하다 |
| **apex 판정** | **우리가 하지 않고 Vercel `apexName` 에 위임** | `brandA.co.kr` 은 레이블 3개지만 apex 다(Public Suffix List 문제). 한국 브랜드가 주 대상이라 자체 판정하면 **첫 고객부터 잘못된 레코드를 안내**한다 |
| **DNS 안내 값** | **하드코딩 금지** — Vercel 응답의 권장값을 저장해 그대로 표시 | `76.76.21.21` / `cname.vercel-dns.com` 은 현재값일 뿐이고 Vercel 이 리전별 타겟으로 옮겨가는 중이다 |
| **세션 쿠키** | **손대지 않는다**(`Domain=.klow.kr` 그대로) | 커스텀 도메인이 세션을 쓰지 않으므로 host-only 전환이 불필요해졌다. 승격 시에만 필요 → [P5](./implementation-plan.md#6-1-풀-프록시-승격--로그인결제까지-커스텀-도메인) |
| **SEO(초기값)** | 커스텀 도메인 전량 **`noindex, follow`**, canonical 은 klow.kr 유지 | 중복 콘텐츠 위험 0. `siteConfig.url` 을 host 인식으로 바꾸면 5개 파일이 request-time dynamic 이 되어 ISR 이점을 잃는다. 브랜드 요구 시 P5 에서 브랜드별로 개방 |
| **구글 로그인** | **별도 작업 없음** | 로그인 진입점 자체가 `klow.kr` 로 나가므로 커스텀 도메인에 버튼이 렌더되지 않는다(구 계획의 "P3 숨김 + P5 핸드오프"가 둘 다 불필요) |

### #0 — Eximbay 도메인 제한 (2026-08-20 조사 · 남은 질문 1개)

> 🟡 **같은 날 설계가 핸드오프로 바뀌면서 이 항목은 착수 블로커에서 내려왔다.** 결제창을 호출하는
> 페이지가 계속 `klow.kr` 이므로 **P0~P4 에는 이 답이 필요 없다.** 아래 내용은 그대로 유효하고,
> [P5 승격](./implementation-plan.md#6-1-풀-프록시-승격--로그인결제까지-커스텀-도메인)을 검토할 때
> **그때 물어보면 된다.**

**결론: 런타임 도메인(Referer) 차단은 없다는 증거를 잡았다.** 남은 제약은 **계약·심사 축**이고,
그쪽이 진짜 블로커다. 그리고 **위험의 성격이 바뀐다** — "결제창이 안 열린다"(즉시 실패)가 아니라
**"결제는 되는데 심사받지 않은 사이트에서 매출이 발생해 매입사 모니터링에 걸려 정산 보류·서비스 중단"**
(조용히 굴러가다 나중에 터짐)이다. P3 를 막는 이유로는 오히려 더 무겁다.

**확인된 코드 사실**: `return_url`/`status_url` 은 `EXIMBAY_RETURN_BASE_SERVER`(= `api.klow.kr`) 고정이라
브랜드 도메인과 무관하고(`payment.service.ts:334-335`), 결제 payload
(`fgkey`/`payment`/`merchant`/`buyer`/`url`/`settings`/`product`)에도 **도메인 파라미터가 없다.**

#### 실측 — 브라우저가 닿는 3개 지점 전부 도메인 무관 (샌드박스)

`javascriptSDK.js` 를 받아 난독화를 풀면 하는 일이 단순하다: 브라우저에서
`POST {api}/v1/payments` → 응답의 `url` + hidden field 로 form 을 만들어 submit.
(`/v1/payments/ready` 는 **우리 서버가 Basic 인증으로** 치므로 브라우저 도메인이 애초에 안 실린다.)
그래서 도메인이 개입할 수 있는 지점이 정확히 3곳이고, 셋 다 찔러봤다 — 테스트 MID `1849705C64` / `api-test`,
Origin·Referer 를 `klow.kr` / `shop.brandA.com` / 무작위 도메인 / 없음 으로 바꿔가며:

| # | 지점 | 결과 |
|---|---|---|
| ① | SDK 의 CORS preflight (`OPTIONS /v1/payments`) | 전부 **`access-control-allow-origin: *`** — origin 을 보고 갈리지 않는 정적 응답 |
| ② | `POST /v1/payments` (브라우저가 치는 결제창 요청) | 전부 **200 + 바이트 단위로 동일한 응답**(게이트웨이 `url` 발급) |
| ③ | 결제창 게이트웨이 `BasicProcessor.krp` form POST | 전부 **200 + `paramkey` 발급 → 결제 1단계 진행** |

> **재현법**: `POST {api-test}/v1/payments/ready` 에 `Authorization: Basic base64(API_KEY + ":")` 로
> fgkey 를 받고 → 같은 payload + fgkey 를 `POST {api-test}/v1/payments` 에 Origin/Referer 를 바꿔가며 보낸 뒤
> → 그 응답의 `url` 로 hidden field + `param3=OPENAPI` 를 form POST 한다.

⚠️ **한계 2개**: (a) **샌드박스**이고 (b) **운영 MID 의 계정별 설정은 외부에서 관측 불가**다.
다만 "MID별 화이트리스트"라면 보통 ②③에 게이트가 걸리는데 **그 계층 자체가 origin 을 안 보는 구조**라
존재 가능성은 낮은 쪽이다. 확정은 여전히 Eximbay 회신으로만 가능하다.

  → 호스팅사 특성일 수 있으나 **"몰(도메인) = 가맹점"으로 본다는 방증**이다
  (아래 표 4번 "단일 MID 복수 도메인"의 **반대 방향** 신호).
- **심사는 사이트·업종 단위이고 사후 모니터링이 붙는다.** [심사 시 웹사이트 준비](https://support.eximbay.com/hc/ko/articles/360052850573):
  *"심사 시 통과한 상품이 아닌 그 외의 상품을 판매할 경우 서비스 이용에 제한이 있을 수 있으며 **정산 지급이 보류**"*,
  [심사 프로세스](https://support.eximbay.com/hc/ko/articles/360044087233): *"매입사/결제사에서는 **정기적으로 모니터링**"*
- **가맹점 정보 변경은 전부 수기 요청이다.** 결제창 가맹점명·로고·사이트 URL 모두 "고객센터로 요청"이고
  ([가맹점명](https://support.eximbay.com/hc/ko/articles/1500000522821) ·
  [로고](https://support.eximbay.com/hc/ko/articles/360049552634)), 백오피스는 거래/정산·서류·권한용이다.
  **셀프서비스 등록 API 는 문서 어디에도 없다.**
- (곁가지) 결제창 가맹점 영문명이 *"업체명(사이트 주소명)"* 규칙이라 **브랜드 도메인에서 결제해도 결제창엔
  KLOW 이름이 뜬다** — 판매 주체가 KLOW 라는 이 설계의 전제와는 오히려 정합이다.

#### 문의 항목별 잠정 답 (번호는 조사 이전 초안 기준)

| 질문 | 잠정 답 | 근거 |
|---|---|---|
| 1. 화이트리스트 존재 / 검사 기준 | 런타임 Referer 검사는 **없음**. 대신 "등록된 사이트 URL" 이 계정 속성으로 존재 | 실측 + FAQ |
| 2. 미등록 도메인이면 거절되는가 | **거절 안 됨** (샌드박스 3지점 전부 통과) | 실측 |
| 3. **등록 자동화 가능 여부** | **거의 확실히 불가** — 모든 가맹점 정보 변경이 고객센터 수기 요청 | FAQ (강함) |
| 4. **단일 MID 복수 도메인 허용 여부** | **미확인 — 남은 진짜 리스크** | 문의 필요 |
| 5. 3-DS / 카드사 심사 유의사항 | 미확인 | 문의 필요 |

⚠️ **3번이 "수기"로 굳었으므로 판단 기준이 4번으로 옮겨간다.** 4번이 **허용**이면 등록 절차 자체가
불필요해져 자동화 문제도 같이 사라진다. **불허**면 브랜드마다 MID 발급(독립몰 기준 심사 진행비 33만원 +
결제사 심사 2~4주)이라 **P5 승격이 성립하지 않는다** — 그때는 핸드오프 방식이 종착점이 된다.
그래서 메일도 4번을 맨 앞에 놓도록 다시 썼다.

ℹ️ **지금 당장 보낼 필요는 없다.** P0~P4 는 이 답과 무관하고, [P5 승격](./implementation-plan.md#6-1-풀-프록시-승격--로그인결제까지-커스텀-도메인)을
검토하기로 할 때 보내면 된다(회신에 2~4주가 걸릴 수 있으므로 **검토 시작과 동시에** 보낼 것).

## 검토했으나 채택하지 않은 안

재논의를 막기 위해 기록해 둔다. 되돌리려면 **여기 적힌 근거가 먼저 무너져야 한다.**

| 안 | 왜 안 골랐나 |
|---|---|
| **결제까지 커스텀 도메인** (same-origin 프록시 — 2026-08-19 원안) | 카페24·쇼피파이와 같은 "사이트 전체" 모델이고 브랜드 요구에 가장 충실하지만, **프록시 Route Handler + 쿠키 host-only 전환 + 실 IP/Throttler 배선 + 결제 리턴 재검증(오픈 리다이렉트 표면) + 구글 핸드오프**가 전부 따라오고 **Eximbay 심사 축(#0)** 이 착수를 막는다. 얻는 것은 "결제 직전 주소창이 안 바뀐다" 하나 → **P5 승격으로 미룬다**(설계는 §6-1 에 온전히 보존) |
| **브랜드관 한 페이지만 커스텀 도메인** (제품 클릭 시 klow.kr 로 이동) | 구현은 가장 싸지만 **사용자가 요구한 범위가 아니다**(사이트 전체). 카페24·쇼피파이 어느 쪽도 이 절충을 하지 않는다 |
| **`next.config.js` rewrites 로 프록시** | 요청 헤더를 추가할 수 없어 **실 클라이언트 IP 를 전달할 방법이 없다** → `Order.agreementIp`(PG 분쟁 증거) 오염. `trust proxy` 를 2로 올려 우회하면 직접 호출 경로에서 XFF 위조가 열린다. `implementation-plan.md` §6-1(b) |
| **Cloudflare for SaaS (Custom Hostnames)** | klow.kr DNS 가 이미 Cloudflare 라 후보였다. 그러나 **오리진이 Vercel** 이라 Vercel 도 그 호스트를 알아야 하고(Host 기반 라우팅), Host 를 바꿔 넘기는 Worker 가 추가로 필요해 체인이 한 단 더 길어진다. 도메인 수가 **수백 개 규모**가 되면 재검토 가치가 있다 |
| **운영팀이 Vercel 대시보드에서 수동 등록** | 1단계로는 가장 안전하지만 브랜드가 늘 때마다 사람이 개입해야 한다. Vercel Domains API 로 자동화가 되므로 처음부터 자동으로 간다 |
| **`klow.kr/{slug}` → 커스텀 도메인 301** (쇼피파이 primary domain 방식) | 브랜드 SEO 에는 유리하지만 프로모션 링크·시딩 링크·현장 QR·카페24 임베드가 **전부 한 번씩 튀고**, `/shop` 에서 브랜드관에 들어가도 도메인이 바뀐다. **사용자가 "둘 다 살려두기"를 선택**했다 |
| **klow.kr 도 프록시를 태워 경로 통일** | 디버깅 일관성이라는 장점은 있으나 klow.kr↔api.klow.kr 은 same-site 라 **지금 아무 문제가 없다**. 전 트래픽에 Vercel 함수 비용과 1홉 지연이 얹히고 회귀 위험만 커진다 |
| **`Brand.customDomain` 단일 컬럼** | apex 와 `www` 는 Vercel 에 각각 등록해야 하는 별개 도메인이고 레코드 타입도 다르다. 검증 상태 머신과 Vercel 챌린지 원문을 담을 곳도 없다 |
| **커스텀 도메인 self-canonical + index (초기부터)** | `siteConfig.url` 을 host 인식으로 바꾸려면 5개 파일이 request-time dynamic 이 되어 ISR 이점을 통째로 잃는다. 브랜드가 소수인 초기엔 손해다. 브랜드 요구 시 P5 에서 **브랜드별 플래그**로 개방 |
