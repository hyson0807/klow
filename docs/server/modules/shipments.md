# shipments — EFS 송장 발급/추적

- **모듈 경로**: `src/modules/shipments/`
- **주 클라이언트**: 어드민 송장 탭(`klow_admin`, `/admin/shipments/*`) + 브랜드 스튜디오 발송 화면(`klow_brand`, `/v1/brand/shipments/*`).
- **데이터 모델**: `Shipment`(1 브랜드 송장 = 1 박스, `status`/`carrier`/`efsServiceType`/`efsTrackingNumber`/`requestPayload`/`responseRaw`/추적 캐시 `latestStatusCode`/`latestStatusName`/`latestStatusAt`/`trackingCarrier`/`trackingEvents`/`trackedAt` + `submittedAt`/`cancelledAt`/`brandConfirmedShippedAt`/`createdById`), `ShipmentItem`(`orderItemId` @unique 로 OrderItem 1:1 연결 — 동시 발급 race 방지), `ShipmentStatus` enum.
- **한 브랜드 = 한 EFS 송장 = 한 박스**: 한 주문이 N 개 브랜드 제품을 담으면 송장도 N 장 발급된다 — `Shipment` 1개 + `ShipmentItem` N개(그 브랜드의 OrderItem 라인들). 각 브랜드가 자기 박스만 EFS 창고로 발송하기 위함. 제품 라인은 `Product.brandId`, 제품 없는(직접 입력) 시딩 라인은 `OrderItem.brandId` 스냅샷으로 브랜드 그룹핑한다(`groupByBrand`).
- **발급 단위 = (orderId, brandId) 그룹**: 단일 그룹 발급은 `createForBrand`(어드민 `POST /admin/shipments/order/:orderId/brand/:brandId`), 주문 전체 미발급 그룹 일괄 발급은 `createForOrder`(`POST /admin/shipments`). `createForOrder`/`createForBrand` 는 `adminId=null` 로도 호출 가능(결제/시딩 완료 시 시스템 자동 발급, `createdById=null`).
- **어드민 대기 탭 = `listPendingGroups`**: 행 단위는 주문이 아니라 **(주문 × 브랜드) 그룹**이다. 주문 조건은 `paymentStatus='paid'` + `status ≠ cancelled` + **`channel ≠ onsite`** 이고, 거기서 쪼갠 그룹 중 송장이 `pending`/`submitted` 가 **아닌 것**(= 송장 없음 · `failed` · `cancelled`)만 남는다. ⚠️ **주문 status 는 `cancelled` 만 거른다** — `completed`/`shipped` 여도 그 브랜드 몫 송장이 없으면 계속 남으므로(다브랜드 주문에서 실제로 그렇다) "완료된 주문인데 왜 대기에 있느냐"는 오해가 아니라 정상이다. ⚠️⚠️ **현장(onsite) 제외는 필수다** — 현장 결제는 부스 직접 전달이라 `payment.markPaid` 가 송장 생성을 스킵하고 곧바로 `completed` 로 보내는데, 채널을 안 거르면 "결제완료 + 취소 아님 + 송장 없음"을 영원히 만족해 **발급될 일이 없는 그룹이 무한히 쌓인다**(2026-08-20 에 실제로 그러고 있었다 — dev 기준 대기 92건 중 34건이 현장). ⚠️ **브랜드를 못 푸는 라인은 조용히 빠진다** — 제품이 하드 삭제됐고 `OrderItem.brandId` 스냅샷도 없으면 `continue` 라 어느 탭에도 안 뜬다(현재 실제 현장 주문 4건이 이 상태라 위 버그가 실데이터로는 안 보였다). ⚠️ 조회 폭은 **최근 `take×4` 주문**(기본 100 → 400)이라 그보다 오래된 미발급 주문은 목록에 없다. 회귀 잠금은 `__tests__/pending-groups.spec.ts`(현장 제외 · 송장 상태별 잔류 · 다브랜드 부분 발급).
- **어드민 출고관리에 `발급완료` 탭은 없다 (2026-08-20 제거)**: 발급된 송장 목록은 **`/tracking`(송장 추적)이 단독으로 담당**한다 — 브랜드·국가·추적상태 필터와 검색·정렬·페이지네이션·추적 갱신을 갖춰 같은 것을 더 잘 보여주기 때문이다. 제거된 탭은 그 부분집합을 필터 없이 `listAdmin` 기본 `take:100` 으로 조용히 자르고 **잘린 배열 길이를 그대로 "총 N건"으로 표시**하고 있었다(제거 시점 실측 `submitted` 111건 중 11건이 어느 화면에도 안 보였다). 출고관리 헤더에 `/tracking` 링크를 남겼으니 **같은 목록을 다시 만들지 말 것** — 두 화면이 되면 필터·잘림 규칙이 곧 갈린다. 남은 탭은 `대기`/`실패`/`삭제됨` 셋이고, 발급 성공 여부는 발급 직후 토스트 + 대기 탭에서 그룹이 사라지는 것으로 확인한다.
- **송장 상태 전이 (`ShipmentStatus`)**: `pending`(row 생성 + EFS 호출 전) → EFS 회신 성공이면 `submitted`(+`efsTrackingNumber`/`localCarrierName`/`localTrackingNumber`/`submittedAt`), 회신 N 또는 네트워크 throw 면 `failed`(+`errorMessage`). 취소는 **실제 EFS 취소**다 — `markCancelled`(어드민) / `cancelForBrand`(브랜드, 소유권 확인 후) 모두 `performEfsCancel` 로 EFS `changeShipment` 에 `{송장번호}|Cancel` 을 보내고, 성공해야 `cancelled`(+`cancelledAt`)로 마킹한다(이미 `cancelled` 면 멱등 반환). 취소 가능 대상은 `submitted` + EFS 송장번호가 있는 송장뿐이고(아니면 400), EFS 가 거부하면(예: 픽업 후) **DB 를 건드리지 않고 502** 로 사유를 그대로 올린다. 취소 후처리는 주문 종류로 갈린다 — **시딩 주문이면 완전 취소**(`Order.status='cancelled'` + `SeedingLink.status='cancelled'` 한 트랜잭션 → 재사용 불가), 일반 주문이면 `maybeRevertOrderFromShipped` 로 `processing` 복귀(재발급 가능). `failed`/`cancelled` 는 **재발급 가능 상태**(`isReissuableStatus`) — 같은 row 를 `pending` 으로 리셋해 재발급(`retry` → `createForBrand`). `submitted`/`pending` 은 재발급 거부(`ConflictException`). **수화인 수정 재발급**: 이미 `submitted` 된 송장은 수화인(주소)을 고쳐도 EFS `ChangeCnee` 가 US City,State 를 못 담으므로, 어드민이 `PATCH /admin/orders/:id/recipient` 로 수화인을 고친 뒤 `cancelAndReissue`(`POST /admin/shipments/:id/cancel-reissue`)로 **취소+즉시 재발급**해 새 송장번호를 받는다(EFS 픽업 후면 502).
- **국내 자체배송 (`carrier='DOMESTIC'`, 2026-08-13)**: 한국 시딩은 브랜드가 자기 국내 택배로 직접 보내므로 **EFS 송장을 발급하지 않는다**. 그래도 `Shipment` 행은 만든다 — 브랜드 발송대기 탭 조인·발송처리 버튼·중복 수령 경고(`attachSeedingDuplicates`)·`Order.status` 전이가 전부 이 행(과 `ShipmentItem`)을 읽으므로, 행이 없으면 국내 건은 **어느 화면에도 뜨지 않는다**.
  - `executeCreate` 가 국내면 **송화인 검증·`buildPayload`·EFS 호출을 전부 건너뛰고** `pending` 없이 곧바로 `submitted`(+`submittedAt`)로 쓴다. `efsTrackingNumber=null`, `efsServiceType='DOMESTIC'`, `requestPayload={domestic:true,…}`. 송화인 정보는 EFS payload 전용이라 국내 발송엔 요구하지 않는다.
  - ⚠️ **`payload-builder` 는 DOMESTIC 을 타입에서 배제**한다 — `CARRIER_TO_EFS_SERVICE_TYPE` 이 `Record<Exclude<ShippingCarrier,'DOMESTIC'>, string>` 이고 `mapServiceType` 이 throw 한다. 아무 문자열이나 매핑해두면 호출부의 국내 분기가 빠졌을 때 **실제 EFS 발급 요청이 나간 뒤** `Service type is invalid` 로만 드러난다.
  - **취소**: `cancelEfsShipmentOnly` 가 국내면 EFS `changeShipment` 없이 상태만 `cancelled` 로 되돌린다(송장번호를 요구하는 가드를 그대로 태우면 국내 건은 취소 자체가 400 이다). 시딩 캐스케이드(주문 취소 + claim 취소 + **정원 반납**, single 링크는 링크까지)는 그대로다. `cancelAndReissue` 는 국내 건을 400 으로 거절한다(EFS 에 고칠 송장이 없다).
  - **발송 처리 = 완료**: 종착 판정의 단일 출처는 **`isTerminalShipment(s)`** 다 — `submitted` 이면서 EFS 는 배송완료 추적 코드, 국내는 `brandConfirmedShippedAt` 이 있으면 종착이다. 기존 `maybeMarkOrderCompleted` 가 이 술어를 그대로 쓰므로 `confirmShippedForBrand` 는 그 훅을 부르기만 한다(국내 건일 때만 — EFS 송장은 발송 확인만으로 종착이 될 수 없어 결과가 안 바뀌는데 부르면 조회가 통째로 버려진다). `unconfirmShippedForBrand` 는 `maybeRevertOrderFromCompleted` 로 대칭 복구(`completed → shipped`). 이 때문에 klow_brand 시딩 탭에서 국내 건은 **배송중을 건너뛰고 바로 시딩기록**으로 간다.
    - ⚠️ **국내 전용 완료 훅을 따로 두지 말 것.** 처음엔 `maybeCompleteDomesticOrder` 를 병렬로 만들었는데, 그러면 **국내·EFS 송장이 섞인 주문이 양쪽 어디에도 안 걸려** 영영 `shipped` 에 머문다(EFS 훅은 국내 송장이 못 받는 배송완료 코드를 기다리고, 국내 훅은 전 라인이 국내이길 요구한다). 술어 하나로 합치면 섞여도 맞는다.
  - **취소는 캐리어가 아니라 `efsTrackingNumber` 유무로 갈린다** — 추적 갱신·cron·efs-billing 이 모두 그 기준으로 "EFS 소유 여부"를 판정하므로 여기만 캐리어로 물으면 같은 질문에 축이 둘 생긴다. 국내 건은 발급한 게 없어 자연히 외부 취소를 건너뛴다.
  - **구조적으로 제외되는 곳**: 추적 갱신·cron·efs-billing 은 모두 `efsTrackingNumber: { not: null }` 로 이미 거르고, 정산은 `latestStatusCode = 배송완료 코드`를 요구한다. ⚠️ **정산 제외가 안전한 건 국내 시딩이 브랜드 결제(₩0) 전용이기 때문**이다 — 유료 국내 시딩을 열면 여기서 조용히 미정산된다.
  - 고객 `/track` 은 `shipmentTrackingStatus` 의 DOMESTIC 분기로 `submitted` 를 돌려준다(안 그러면 `!trackingNumber → preparing` 이라 발송 후에도 영영 "배송 준비 중").
  - klow_brand 화면 주의: **발송대기 행의 `selectable`(인쇄)과 `shippable`(발송처리)은 다른 플래그**다(합치면 국내 건이 발송대기에 갇힌다). 스튜디오 배송 상세의 **EFS 인천 GDC 입고지 안내는 국내 건에서 반드시 숨긴다** — 국내는 수령인에게 바로 보내므로 안내대로 하면 박스가 엉뚱한 곳으로 간다.
- **EFS 연동 (`efs.client.ts`)**: `EFS_API_BASE`(기본 `http://www.efs.asia:200/api/in/`) 로 form-encoded(`apikey`/`req_function`/`send_data`) POST, 15s 타임아웃. 호출은 네 가지 — `newCreateShipment`(발급) · `changeShipment`(취소, `{송장번호}|Cancel`) · `getTrackStatusALL`(추적 이벤트 타임라인) · `getTrackStatus`(단수/배치 — 라스트마일 배송번호·실측무게·EFS 배송비 `chargeKrw` 를 주는 유일한 호출, efs-billing 이 재사용). `EFS_API_KEY` 가 비어 있으면 **dev mock** — 가짜 송장번호 `XXX...` 발급 + 합성 추적 이벤트(01/03/11) 반환. 응답 봉투는 단일행(문서/mock) / 둘째 줄 데이터(실서버 QT) 두 포맷 모두 파싱(`parseEfsEnvelope`), ack 실패만 `BadGatewayException`. 발급 성공 판정은 데이터필드 `Y`. **배송완료 코드 집합 `EFS_DELIVERED_CODES = ['33','47','74']`**(배송완료/수취인 수거/종료 처리)과 판정 헬퍼 `isDeliveredTrackingCode()` 를 이 모듈이 정본으로 소유한다 — klow_admin `lib/tracking-status.ts` 의 delivered 카테고리와 같은 집합이고, 주문 자동 완료·고객 배송추적·cron 종료 판정이 모두 여기서 파생된다.
- **payload 빌드 (`payload-builder.ts`)**: `buildPayload` 가 33 필드를 `|` join 한 `sendData` 를 만든다. 핵심:
  - **24번 itemCapsule (multi-item)**: 기본은 그룹 라인 수만큼 `{"...",...},{"...",...}` 콤마로 이어붙인 블록(라인별 쇼핑몰명 KLOW/주문번호/상품번호/영문 상품명/통관 카테고리/HS code/수량/USD 단가/상품 URL). `,`/`|`/`{}`/`"` 충돌은 sanitize. **예외 — 시딩 라인은 신고 제품 수만큼 캡슐로 펼쳐진다**(고객 선택은 바이어가 고른 제품, 브랜드 지정은 발급 시 동결한 제품. 펼친 각 서술자의 수량 = 1, 합 = `OrderItem.quantity`. 파생은 [seeding](./seeding.md) 의 `customsCapsuleProducts()`). ⚠️ **펼친 뒤 같은 상품(24-4 상품번호·24-5 품명·24-11 단가가 모두 같은 것)은 캡슐 1개로 합치고 24-9 수량만 더한다**(`mergeCapsuleItems`) — EFS 는 반복 캡슐이 아니라 **Qty** 로 개수를 표현하고(스펙 v3.5 의 `changeShipment/ChangeItem` 예시), 변형이 다를 때 나누라고 24-7 옵션이 따로 있다. 중복이 들어오는 실경로는 둘 다 시딩이다 — ① 브랜드 지정 링크에서 **등록 제품 < 박스당 수량** 이면 발급 시 같은 제품을 반복 추출한다(`randomCustomsProductNames` — 실제로 박스에 여러 개 들어가므로 그 반복 자체는 정상. ⚠️ 거기서 중복을 없애면 개수가 줄어 아래 펼침 가드에 걸려 신고가 통째로 일반 품명으로 떨어진다), ② 옛 한글 라벨 링크는 non-ASCII 라벨이 전부 동결 영문 품명으로 폴백해 캡슐이 겹친다. 병합 키는 **sanitize·slice·round2 를 거친 렌더 후 값**이라 구분자 치환 뒤 같아지는 캡슐도 접힌다(⚠️ 키에서 상품번호를 빼면 품명만 같은 다른 제품이 한 줄로 뭉쳐진다). 수량 합과 26번은 불변이다. ⚠️ **그때도 `group.lines` 는 절대 늘리지 않는다** — `ShipmentItem.orderItemId` 가 `@unique` 라 `create: lines.map(...)` 이 P2002 로 터진다. 펼침은 오직 `BuildPayloadLine.capsuleProducts` 로 표현하고 빌더가 캡슐 단계에서 편다.
  - **27번 배송비 = 브랜드별 스냅샷 안분**: `perBrandShareUsd(order, brandId, brandCount)` 가 주문 시점 스냅샷 `Order.shippingFeeByBrand[brandId]` 를 읽는다 — 무료배송 브랜드는 0. 스냅샷이 없는 legacy 주문(2026-07-28 이전)만 `shippingFeeUsd/brandCount` 균등분배로 폴백한다. 한 주문의 모든 송장 share 합 = 총배송비. (배송비 정본·절반 분할 규칙은 [shipping](./shipping.md) 모듈.)
  - **2번 발송품 참조번호(20자)**: EFS 가 취소된 송장의 참조번호 재사용을 거부하므로(QT 확인), 발급마다 service 가 유일 토큰(`Date.now().toString(36)`)을 주입해 `order.id 끝7 + brand.id 끝4 + 토큰` 으로 만든다. 토큰이 없는 preview/test 경로만 `(orderId, brandId)` prefix 로 derive(EFS 미전송이라 무방).

  - **`shipment-retry.cron.ts`**(`*/10 * * * *` KST, name `efs-shipment-retry`, `SHIPMENT_RETRY_CRON_ENABLED=false` 로만 비활성)가 `retryDue()` 를 부른다. 백오프는 **5분 → 20분 → 60분**, 상한 `MAX_AUTO_RETRIES=3`. **무한 재시도 방지 3중**: `retryCount < 3` 상한 · 성공/거부 시 `nextRetryAt=null` · 배치 `LIMIT 20`. ⚠️ **카운터는 재발급 호출 前에 올린다** — 도중에 프로세스가 죽어도 다음 사이클이 같은 건을 무한히 다시 집지 않는다(사고 시 한 번 덜 시도하는 쪽으로 실패). 소진하면 `retry-exhausted` 문자를 **1회** 보낸다 — ⚠️ 이 "1회"를 보장하는 건 플래그 컬럼이 아니라 `nextRetryAt=null` 이다(cron 조회가 `nextRetryAt != null` 을 요구하므로 다시 집히지 않는다. 별도 `alertSentAt` 마커를 뒀다가 아무 데서도 읽지 않는 write-only 컬럼이라 걷어냈다). pre-validation throw(송화인 미입력)는 사람이 고쳐야 하므로 즉시 끊고 알린다.
  - ⚠️ **어드민 수동 `retry()` 는 `retryCount` 를 0 으로 리셋**한다 — 운영자가 원인을 고치고 누르는 행위이기 때문이다. 리셋하지 않으면 3회를 소진한 송장은 사람이 고쳐 준 뒤에도 자동 복구가 영영 다시 붙지 않는다.
  - **`pending` 고착 해소**: EFS 호출 중 프로세스가 죽으면 row 가 `pending` 에 남는데 `isReissuableStatus`(failed|cancelled)도 `listPendingGroups`(pending 제외)도 못 잡아 **어느 화면에도 안 뜨고 재발급도 못 하는 고아**가 됐다. `retryDue()` 가 `updatedAt < now − 30분`(`PENDING_STUCK_MS`, EFS 타임아웃 15초 대비 충분한 여유)인 pending 을 `failed` + `nextRetryAt=now` 로 승격해 **기존 재시도 경로가 그대로 주워 가게** 한다. ⚠️ 전용 복구 경로를 따로 만들지 않는 게 핵심이다(판정 축이 둘로 늘면 국내배송 완료 훅 때와 같은 사각지대가 생긴다).
  - 컬럼 `Shipment.{retryCount, nextRetryAt}` + `Admin.{phone, shipmentAlertEnabled}`, 마이그레이션 `20260818100637_add_admin_phone_and_shipment_retry` 는 **추가 전용 → 롤링 배포 안전 · 백필 없음**. ⚠️ 새 cron 이라 `test/app.e2e-spec.ts` 기대 목록이 **7개**로 늘었다. 회귀 잠금은 `__tests__/shipment-retry.spec.ts`(백오프·상한·pending 승격·소진 알림 1회) + `__tests__/shipment-alert.spec.ts`(throw 없이 failed 로 온 송장 인식·다브랜드 합산·번호 없는 수신자 거절·AlreadyIssued 는 알림 없음). 배포 순서는 **klow_server → klow_admin**(반대면 어드민이 서버가 모르는 `phone`/`alert-recipients` 를 호출해 400/404).
  - ⚠️ **배포 직후 수신자를 지정해야 실제로 문자가 간다** — `/admins` 프로필에서 번호를 채우고(슈퍼관리자만 가능) 출고관리 '실패' 탭에서 체크. 둘 중 하나라도 비면 조용히 아무에게도 안 간다.

### EFS 회신 4개 값 수동 수정 (`PATCH :id/efs-fields`, 2026-08-21)

어드민 송장 상세의 **EFS 회신** 카드(`klow_admin` `/shipments/[id]`)가 읽기 전용이라, EFS 가 **안 준 값**(라스트마일 번호 미배정)이나 **잘못 준 값**을 운영자가 메일·전화로 확인해도 DB 를 직접 고치는 수밖에 없었다. 카드에 편집 모드 + **변경 전/후 비교 확인 모달**을 붙이고 이 라우트를 뒀다. `AdminGuard`(super 아님 — 같은 페이지의 취소·재발급과 같은 급)이고 **스키마·마이그레이션 변경 없음**.

⚠️ **이 4개 값은 표시용이 아니다.** 무엇이 따라 움직이는지가 이 기능의 전부다:

| 필드 | 소비자 | 잘못 넣으면 |
|---|---|---|
| `efsTrackingNumber` | 추적 폴링·추적 cron·**EFS 취소(`{번호}\|Cancel` 로 그대로 전송)**·efs-billing **매칭 키(HAWB)**·공개 `/track` | **남의 소포를 추적**해 `latestStatus*`·`trackingEvents` 를 덮고 픽업 이벤트가 `brandConfirmedShippedAt` 을 찍어 `maybeMarkOrderCompleted` 까지 돈다. 취소를 누르면 **남의 송장이 취소**된다 |
| `localTrackingNumber` | `tracking-url.ts` 가 **번호 포맷**으로 USPS/GOFO/SingPost 판정 | 추적 링크가 엉뚱한 캐리어로 간다 |
| `localCarrierName` | 공개 `/track` 의 `carrier: trackingCarrier ?? localCarrierName` | **고객 화면**에 잘못된 배송사명 |
| `efsServiceType` | efs-billing 리포트·엑셀 표시 | 표시만 틀어진다(EFS 로 재전송되지 않는다) |

- ⚠️ **`submitted` 인 송장만** 수정할 수 있다(아니면 400). `pending`/`failed` 는 네 값이 전부 null 이고 재발급이 어차피 EFS 값으로 덮으며, **`cancelled` 송장의 번호를 손으로 되살리면 efs-billing 의 HAWB 매칭이 취소된 건에 다시 붙는다.**
- ⚠️ **송장번호는 비울 수 없다**(zod 가 nullable 이 아니다). `null` 이 되는 순간 그 송장은 추적 cron·수동 추적 갱신·`cancelAndReissue`·**efs-billing 전체**(`efsTrackingNumber: { not: null }`)에서 조용히 빠지고 공개 `/track` 이 `preparing` 으로 되돌아간다. 틀린 번호는 **교체**로 고친다. 반대로 로컬 2필드는 비울 수 있고, 비우면 아래 backfill 이 다시 열린다.
- ⚠️ **송장번호는 `.trim().toUpperCase()` 로 저장한다** — efs-billing 이 HAWB 를 `normalizeHawb`(trim+upper)로 비교해 수기 청구행과 dedupe 하므로 소문자로 저장되면 그 dedupe 를 빠져나가 **같은 배송이 청구서에 두 번** 실린다. (그 함수를 import 하지 않는다 — efs-billing 이 이미 shipments 의 `LOCAL_TRACKING_MAX_LEN` 을 import 해 역방향은 순환이다. `common/` 은 애초에 `modules/` 를 못 본다.)
- ⚠️ 충돌은 **두 테이블**을 본다: 다른 `Shipment`(P2002 를 잡아 **409**) + **`EfsManualBillingRow.hawb`**(DB 제약이 테이블을 가로질러 못 걸려 직접 조회 → 409). 겹치면 `mergeBillingRows` dedupe 에서 **수기 행이 조용히 사라진다**.
- ⚠️ 손으로 넣은 `localTrackingNumber` 는 **EFS 추적 갱신이 덮지 않는다** — backfill 2곳(`refreshTracking`, efs-billing `monthlyReport`)이 "비어 있을 때만" 채우기 때문이다. 즉 **오타는 자가 치유되지 않는다**(그래서 확인 모달이 이 문구를 띄운다). 반대로 `efsServiceType` 은 **재발급하면 EFS 값으로 되돌아간다**(payload 는 매번 `carrier` 에서 재계산 — 수정은 기록·리포트 표시용).
- ⚠️ **EFS 를 호출하지 않는다.** 이건 "EFS 값을 고쳐 달라"가 아니라 **우리 기록을 EFS 실제에 맞추는** 조작이다.
- ⚠️ 서비스가 이전 값을 `logger.warn` 으로 남긴다 — `AdminAuditInterceptor` 는 요청 body(=**새 값**)만 저장하고 **이전 값을 남기지 않아** 잘못 고친 값을 되돌릴 근거가 없다(`deleteFailed` 와 같은 이유).
- 업데이트는 **명시적 allow-list 스프레드**(`...(patch.x !== undefined && { x: patch.x })`)라 `undefined`(미변경)와 `null`(지우기)이 갈린다. zod 는 `patchOf()` 를 **쓰지 않는다**(그 헬퍼는 `.optional()` 만 씌워 `null` 을 못 받는다).
- 회귀 잠금 `__tests__/shipment-efs-fields.spec.ts`(대문자 정규화·빈 값 거부·컬럼 폭·`''`→null·submitted 게이트·P2002 409·수기 HAWB 409·미전송 키 불변). 이 4개 컬럼의 **첫 회귀망**이다(종전엔 `efsServiceType` 2건뿐). 배포 순서는 **klow_server → klow_admin**(반대면 저장이 404).
