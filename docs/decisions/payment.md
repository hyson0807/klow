## 결제 확정 3중 방어선 (2026-08-17)

`pending → paid` 전이는 `markPaid()` 한 곳뿐인데, 예전엔 거기 도달하는 경로가 둘(클라 verify · 웹훅)이고 **둘 다 실패했을 때 복구하는 장치가 없어** 카드는 승인됐는데 주문이 영원히 `pending` 으로 남았다. ⚠️ **핵심 결함은 `return_url` 이 klow_web 을 가리킨 것**이다 — 303 으로 넘어간 `/checkout/redirect` **클라이언트 JS** 가 `POST /v1/payment/verify` 를 한 번 더 호출해야 확정됐고, 그 호출은 `api.payment.verify(qs).catch(() => {})` 로 **fire-and-forget + 에러 전부 삼킴**이었다(2026-06-22 `1acabdb` "optimistic 이동" 이후). 확정 실패가 흔적 없이 사라지고 손님은 언제나 성공 화면을 봤다. **현장(`channel='onsite'`) QR 결제가 특히** 취약했다: ① QR→인앱 브라우저라 카드앱(3-DS) 왕복에서 컨텍스트를 잃고 ② 부스에선 "승인" 뜨면 손님이 폰을 집어넣으며 ③ `verify` 가 **IP 기준 5회/분**이라 부스 공용 NAT 뒤 6번째 결제부터 429였고 ④ 송장·알림톡을 스킵하는 채널이라 하류에서 아무도 모르고 어드민 목록은 미결제를 기본 숨김하며 **정산(`paymentStatus:'paid'`)에서도 빠져 브랜드 매출이 통째로 누락**된다. 이제 **(1) `POST /payment/return`**(klow_server, `public-payment-return.controller.ts` — Eximbay 리턴 POST 를 서버가 직접 받아 그 요청 안에서 확정하고 klow_web `/checkout/redirect?<원본qs>&klow_verified=1` 로 303. 원본 qs 를 그대로 넘기는 이유는 시딩 복귀·부스 성공화면·결제상품만 카트 제거가 브라우저 `sessionStorage` 에만 있는 정보를 쓰기 때문) **(2) 웹훅**(status_url) **(3) `payment-reconcile` 크론(15분)** 3중이다. 3번은 `POST /v1/payments/retrieve` + `key_field='order_id'` 로 **우리 주문번호만으로** 조회한다(`pgTid` 를 모르는 주문에 `verify` 는 못 쓴다) — `payment.status` 가 `SALE`/`AUTH` 면 **기존 `markPaid` 를 그대로 태워** 금액검증·멱등·onsite `completed`·메일·시딩·송장을 재사용하고, `REGISTERED`/`NONE` 은 건드리지 않는다. ⚠️ **금액 불일치는 자동 확정하지 않는다**(`mismatch` — 통화 데싱크는 사람이 판단할 문제). ⚠️⚠️ `/payment/return` 은 **`main.ts` Origin CSRF 가드 예외**에 반드시 있어야 한다(Eximbay form POST 엔 Origin 이 없어 빠뜨리면 **전 결제 403**), 그리고 `/payment/return`·`/webhooks/eximbay` 는 **`@SkipThrottle()`** 이다(확정 경로가 자기 rate limit 에 걸리면 버그 재발). 곁들여 고친 것: `parseFloat("132,000")===132` 라 콤마 섞인 KRW 금액이 **영구 고착**(웹훅도 같은 `markPaid` 를 타 재시도해도 실패)을 만들던 것을 `parsePgAmount()` 로 정규화, 웹훅 IP 비교의 `::ffff:` 정규화, 운영 부팅 가드를 "비어있지 않음"에서 **샌드박스 IP 검출 + `EXIMBAY_RETURN_BASE_SERVER`/`FRONTEND_URL` https 강제**로(`.env.example` 기본값이 샌드박스 IP 4개라 그대로 배포되면 콜백 전부 403 인데 warn 한 줄만 남았다), 조용하던 분기 전부 Sentry 배선. 과거 고착분은 `npm run backfill:reconcile-payments`(dry-run 기본, `-- --apply`, 멱등, `--onsite`/`--days`/`--order`), 건별 복구는 어드민 주문 상세 **결제 재확인**(`PATCH /admin/orders/:id/reconcile-payment`). **스키마·마이그레이션 없음.** 회귀 잠금은 `payment/__tests__/payment-reconcile.spec.ts`(콤마 금액 + onsite reconcile → paid+completed + mismatch 는 비전이). ⚠️ 새 cron 이라 `test/app.e2e-spec.ts` 기대 목록이 **6개**로 늘었다. 배포 순서는 **klow_server 먼저**(구 결제창은 옛 `return_url` 로 돌아오므로 klow_web 의 폴백 verify 경로를 당분간 남겨뒀다). 자세히는 [`docs/server/modules/payment.md`](../server/modules/payment.md).

## `trust proxy` 오설정으로 `req.ip` 가 Railway 엣지 IP 였다 — 웹훅 상시 403 · rate limit 전역 뭉침 (2026-09-04)

스페인 손님의 ApplePay 승인(USD 59.15)이 미결제로 남아 Eximbay 가 "statusurl 전송 실패" 메일을 보내면서 드러났다. ⚠️⚠️ **근본 원인은 Eximbay 쪽이 아니라 `main.ts` 의 `app.set('trust proxy', 1)` 이다** — 주석이 "Railway 엣지 프록시 정확히 1단 뒤"라고 단정했지만 실제로는 `req.ip` 에 **호출자가 아니라 Railway 엣지 IP**(`152.233.15.121`/`152.233.15.123`/`152.233.68.97`, whois 상 CDN77-SGP)가 들어왔다. 검증: 공인 IP 가 `211.177.245.36` 인 로컬에서 `api.klow.kr` 로 요청하니 서버 로그에 그 엣지 IP 가 찍혔고, `X-Forwarded-For` 를 임의로 채워 보내도 판정이 바뀌지 않았다(= XFF 마지막이 엣지, 그 **바로 앞**이 실제 클라이언트). ⚠️⚠️ **조사 초기에 그 엣지 IP 를 "Eximbay 발신 IP" 로 오인해 `152.233.14.0/23`·`152.233.68.0/23` 을 화이트리스트에 넣었다가 엔드포인트가 인터넷에 열렸다 — Railway 를 통과한 모든 요청이 매칭되므로 그건 화이트리스트를 끄는 것과 같다. 이 대역을 다시 넣지 말 것.** **망가져 있던 것 셋**: ① Eximbay status_url 화이트리스트가 **구조적으로 매칭 불가**(무엇을 넣든 전부 403 — 웹훅 2차 방어선이 배포 이래 한 번도 동작한 적 없다) ② **`ThrottlerGuard` 의 기본 `getTracker` 가 `req.ip`** 라, 전 세계 트래픽이 엣지 IP 몇 개로 뭉쳐 전역 60회/분·`THROTTLE_TIGHT` 5회/분이 **서비스 전체 합산** 제한이 됐다(CLAUDE.md 가 "부스 공용 NAT 뒤 6번째 결제부터 429"라고 적어 둔 현상의 실제 원인일 수 있다) ③ `Order.agreementIp`(PG 심사용 동의 증거)·`AdminLoginAttempt.ip`·`AdminAuditLog.ip` 가 전부 엣지 IP 라 증거 가치가 없다. ⚠️ 관리자 로그인 락아웃은 **email 기준**이라 영향 없다. **고친 것**: `trust proxy` 를 **`TRUST_PROXY_HOPS` env(기본 2)** 로 뺐다 — 잘못 잡으면 IP 판정이 통째로 어긋나므로 **재배포 없이 되돌릴 수 있어야** 한다. ⚠️⚠️ **홉 수는 과하면 위험하다** — 실제보다 크면 공격자가 XFF 에 넣은 값이 `req.ip` 가 되어 rate limit·화이트리스트가 우회된다. ✅ **2 가 맞다 — 2026-09-05 운영 실측 검증 완료**: 화이트리스트를 `127.0.0.1` 로 두고 공인 IP `211.177.245.36` 인 머신에서 6패턴으로 호출한 결과 **6건 모두 `req.ip` 가 호출자 IP** 였고, XFF 에 화이트리스트 값을 1·2·3개로 채워 넣어도 **전부 403**(우회 불가)이었다. Railway 엣지가 항상 실제 소켓 주소를 append 해 공격자는 XFF 의 **앞쪽만** 채울 수 있다. 값을 바꾸거나 앞단 인프라가 바뀌면 같은 방법으로 재검증한다(어긋나면 env 를 1 로 되돌린다). 화이트리스트 파서는 `payment/webhook-ip-allowlist.ts` 로 빼서 **CIDR 대역**을 받게 했고(⚠️ 빈 문자열 = 미적용 `null` vs 항목이 있는데 전부 형식 오류 = 전부 거부 빈 배열을 **구분**한다 — 후자를 `null` 로 접으면 오타 하나가 화이트리스트를 통째로 끄고 그 사실이 아무 데도 안 남는다. `/0` 은 항목째 버린다), 403 **거부**와 **통과** 양쪽에 소스 IP + `order_id` 를 로그로 남긴다(IP 만 남기던 탓에 어느 주문이 영향받았는지 알 수 없어 이번 사고도 Eximbay 메일로 알았다. 미인증 입력이라 **개행 제거 + 64자 절단**으로 로그 인젝션을 막는다). ✅ **Eximbay 운영 발신 IP 는 `15.165.144.33` 하나로 확정**(2026-09-05, `trust proxy` 수정 후 재전송으로 실측 — **공식 문서 값이 맞았다**). 문서가 함께 안내하는 `172.28.11.71`/`172.28.11.72` 는 사설 대역이라 외부 출발지가 될 수 없고 관측되지도 않았다. 즉 **이 사고에 Eximbay 잘못은 없었고 원인은 100% 우리 `trust proxy` 설정**이었다. ⚠️⚠️ **운영에서 `EXIMBAY_WEBHOOK_IPS` 를 비우면 `main.ts` 가드가 부팅을 거부해 서비스 전체가 502 다** — 화이트리스트를 잠시 풀려고 값을 지웠다가 실제로 전면 장애를 냈다. 풀어야 하면 더미 값(`127.0.0.1`)을 넣을 것. ⚠️ 화이트리스트 제거는 기각했다 — 위조 방어는 이미 Eximbay 재조회(`eximbayFetch` 가 `rescode!=='0000'` 이면 throw) + 금액검증 + `pgTid @unique` 가 하지만, 이 라우트가 **`@SkipThrottle()`** 이라 화이트리스트를 빼면 인증도 rate limit 도 없는 공개 엔드포인트가 되어 요청 하나가 DB 조회 + Eximbay API 호출(타임아웃 10초)을 유발한다(**우리 서버가 Eximbay 를 두들기는 증폭기**). **곁들여 확인된 사실**: `/payment/return`(브라우저 리다이렉트)은 **원래 ~12% 실패**한다 — 카드결제 76건 중 **9건(11.8%)** 이 크론/백필로 뒤늦게 복구됐고 그중 **6건이 `onsite` 부스 QR** 이다(판별은 `paidAt` 의 **분이 15의 배수 + 초 < 5** 라는 크론 지문으로 한다 — `paidAt - createdAt` 지연으로 세면 손님이 결제창에 머문 시간이 섞여 과대집계된다). 즉 웹훅이 죽어 있는 동안 그 12% 가 그대로 미결제 고착이 됐고, 3중 방어선이 고장을 **고친 게 아니라 숨겼다**. **마이그레이션·라우트·cron·스키마 전부 불변 · klow_web/klow_admin/klow_brand 무변경.** 회귀 잠금은 `payment/__tests__/webhook-ip-allowlist.spec.ts`(14 — 대역 경계·`/32` 폴백·`::ffff:` 정규화·**미적용 vs 전부거부**). ⚠️ 남은 과제: `trust proxy` 검증 → Eximbay 실제 IP 확보 → 화이트리스트 재설정, 그리고 24시간 창(`PENDING_ORDER_TTL_MS`)을 넘겨 크론이 못 잡는 과거 미결제(결제창까지 간 것 55건) 전수 점검(`npm run backfill:reconcile-payments -- --days 365`, ⚠️ 프로덕션 Eximbay 자격증명이 필요해 로컬에서는 못 돌린다).

## ⚠️⚠️ PG 실패 콜백이 결제완료로 확정된 사고 — `rescode` 게이트는 `parseAndMarkPaid` 안에 (2026-09-10)

`rescode` 검사가 **공유 함수가 아니라 `handleReturn` 호출부 한 곳에만** 있었고, `parseAndMarkPaid` 진입점 **3개 중 2개**(`handleStatusWebhook`, klow_web 폴백 `verify`)가 그 검사를 통째로 건너뛰었다. **2026-09-09 FOURSUMMER 현장결제(NAVER Pay(Card), `payment_method=P307`)**: 19:39:48 인증 성공 → `return_url` 이 `rescode=0000` → **paid 확정** / 19:39:49 최종 승인 **실패** → `status_url` 이 `rescode=X059`(도난분실 카드)·`8327`(한도 초과)로 통보했는데, 웹훅이 rescode 를 안 보고 `markPaid` 직행 → 이미 paid 라 `count===0` → **"같은 tid 로 이미 paid → 멱등 성공"** 분기로 조용히 삼켜지고 우리 서버가 Eximbay 에 `rescode=0000&resmsg=success` 를 회신했다. **PG 는 실패를 정확히 통보했는데 우리가 성공 재통보로 오인**한 것이다. 주문 2건이 결제완료로 남아 브랜드 정산에 ₩39,130 이 잡혔다(미정산이라 지급 전 정정 — `paymentStatus=failed`/`status=pending`/`paidAt=null`, ⚠️ `pgTid`·`paymentMethod` 는 PG 실패 거래와 대조할 증거라 남겼다). ⚠️ **게이트를 호출부로 되돌리지 말 것** — 진입점이 늘 때 빠지는 게 사고의 원인 그 자체다(`handleReturn` 의 중복 분기도 제거했다). ⚠️ 게이트는 **`verify` 호출보다 앞**이다(실패 콜백은 Eximbay 왕복을 만들 이유가 없고, 뒤에 있으면 통과 시 그대로 `markPaid` 로 이어진다). ⚠️⚠️ **이미 paid 인데 PG 가 실패를 통보한 모순**은 `rejectFailedCallback` 이 ERROR + Sentry 로 올린다(예전엔 흔적조차 없었다) — **자동 강등은 안 한다**(그 주문엔 이미 송장·확인메일·카트정리·정산 후보가 붙어 있을 수 있어 결제 상태 하나로 안 끝난다). `markFailed` 가 `pending` 에서만 전이하므로 이 게이트가 정상 결제를 강등할 수는 없다. ⚠️⚠️ **`verify` 는 결제 성공 판정이 아니다** — `/v1/payments/verify` 는 **querystring 위변조 검증(무결성)** 이고 `eximbayFetch` 는 **봉투 `rescode`** 만 본다(회귀 스펙이 그 응답을 `{rescode:'0000'}` 로만 목킹하는 게 그 가정의 증거). 실제 결제 상태 정본은 `retrieve` 의 `payment.status ∈ {SALE, AUTH}` 이고 **재확인 크론만** 그걸 본다. ⚠️ **그 크론은 `pending` 만 본다** — 한 번 잘못 `paid` 가 되면 다시 검사하지 않아 **영구히 남는다**. **마이그레이션·라우트·cron 전부 불변 · klow_web/admin/brand 무변경.** 회귀 잠금은 `payment/__tests__/failed-callback-gate.spec.ts`(13) — **세 진입점 전부** × 실제 사고 파라미터(X059/8327 원문). ⚠️ 하나만 검사하는 스펙으로 줄이지 말 것. **수정 전 코드로 돌리면 9개가 실패한다**(스펙이 실제로 이 버그를 잡는다는 증거). **알려진 갭**: PG 응답 원문을 저장하지 않아 사후 규명이 PG 콘솔 대조에만 의존한다(이번에도 스크린샷을 받고서야 특정했다) — 결제완료 74건 중 같은 방식으로 오확정된 건이 더 있는지 DB 만으로는 판별 불가. 자세히는 [`docs/server/modules/payment.md`](../server/modules/payment.md).
