## 결제 배송비 + 무료배송 (2026-07-28)

고객은 판매가와 **별도로** 배송비를 낸다 — `500g 요율/fx × 청구 대상 브랜드수`(한 브랜드 = 한 송장). ⚠️⚠️ **2026-09 전환: 그 선결제분은 브랜드 정산금으로 전액 지급된다** — 예전엔 브랜드 실측 물류비의 '선납금'이라 차액만 후청구했지만(`max(0, 실비+수수료−선결제)`), 지금은 고객이 낸 배송비를 브랜드가 다 받고 EFS 실비+수수료를 전액 후청구한다. 요율표와 실비의 차액은 **브랜드 손익**이다(아래 정산·efs-billing 항목). **⚠️ 2026-07-30 전환: 기준이 `2kg 요율의 절반` → `500g 요율 그대로`** 로 바뀌었다(절반 나눗셈 폐지). 요율표는 고정비 비중이 커서 무게 비례가 아니라 **98개국 중 96개국에서 배송비가 올랐고**(중앙값 +24%, 내려간 곳은 US·PH), 그만큼 브랜드 후청구액은 줄었다. 공개 응답 필드는 `logisticsCost2kgKrw` → **`customerShippingKrw`**(무게 중립 rename, 서버가 과도기 동안 구 이름 병기). 캐리어 근사만 2kg 유지(`CARRIER_FALLBACK_WEIGHT_G`). `Order.shippingFeeByBrand` 스냅샷 덕에 **기존 주문 소급 영향 없음** — 마이그레이션·백필 없음. **무료배송은 국가별 설정**(`ProductCountryPrice.freeShipping`, **2026-07-29 전환** — 구 전역 `Product.freeShipping`·`Brand.freeShippingAll` 컬럼과 두 PATCH 엔드포인트는 제거됨)이라 같은 제품도 미국은 무료·일본은 유료가 된다. 판정은 `resolveFreeShipping(row, iso2)` 단일 출처이고 **행이 없는 국가 = 유료**(fail-closed — `(cp)` 대신 `(row, iso2)` 를 받아 목적국 필터를 빠뜨려도 배송비가 안 샌다). 켜면 고객이 배송비를 안 내고 실측 **전액**이 브랜드 몫. 배송비가 브랜드 단위라 **그 브랜드 라인이 전부 무료일 때만** 면제된다(`pricing/chargeable-brands.ts` `chargeableBrandIds(lines, iso2)` — 주문 생성·견적 공유). 브랜드별 금액은 `Order.shippingFeeByBrand`(JSON `{brandId: 센트}`, Σ == `shippingFeeUsd`)에 스냅샷해 송장 발급이 EFS 27번을 정확히 안분한다(legacy 주문 null → 균등분배 폴백). ⚠️ 물류비/캐리어 미설정국·EFS 제외구역 차단은 **요금이 아니라 배송 가능 여부 게이트**라 무료배송이어도 그대로 막는다. 박스 규격(`Product.weightG` + `box{Length,Width,Height}Cm`)은 **제품 공용**(국가별 아님) 값으로, 국가별 예상 배송원가(청구중량)와 캐리어 무게 분기의 입력일 뿐 가격/고객 결제 배송비와 무관 — 제품 create/PATCH payload 로 저장한다(전용 `/box` 엔드포인트 제거). ⚠️ 공개 응답의 `freeShipping` 은 `?country=` 기준 파생값이라 카트/스토어에 스냅샷하면 배송지 변경 시 어긋난다 — klow_web 카트 라인엔 이 필드가 없고, 배송비 금액·라벨은 `POST /v1/orders/quote` 만 정본이다. 브랜드 UI: **국가별 판매가 설정 모달** 하나에서 그 나라 판매가·할인·무료배송 스위치를 정하고, 같은 모달에서 박스 규격(실무게·치수)을 넣어 "고객 부담 vs 무료배송" 브랜드 부담액을 비교한다 — 박스 규격만 제품 공용이라 어느 나라 모달에서 고쳐도 전 국가에 반영된다. 실측 후청구 정산은 어드민 **배송비 청구** 탭(efs-billing).

## 브랜드 취급 품목 = 통관 분류 정본 (2026-07-31)

`Brand.category`(prisma enum `BrandCategory`: `cosmetics` | `dental_materials`, **nullable — `null` = 아직 안 고름**)가 **EFS 24-6 영문 통관 분류 / 24-8 HS 코드의 단일 출처**다. 품목은 **첫 제품보다 먼저** 정해진다 — 서버가 품목 없이는 제품 생성을 거부하고(`assertBrandCategoryChosen`, 단건 + 일괄 초안 양쪽), 값 자체는 **가입 직후 `/start` 2단계**에서 브랜드 생성과 동시에 정해진다(2026-08-25 전환 — 아래 별도 항목). ⚠️ **묻는 시점이 두 번 옮겨졌으니 되돌리지 말 것**: 로그인 직후 온보딩 첫 화면(~2026-08-11) → 제품 등록 진입점을 가로채는 `categoryGate`(~2026-08-25) → 지금의 `/start` 2단계. 중간 단계의 이유였던 "브랜드관을 안 쓰고 시딩·링크만 쓰는 브랜드에게 평생 안 쓸 값을 강요한다"는 여전히 참이지만, **그 값이 시딩 송장의 통관 분류이기도 해서** 브랜드관을 안 써도 결국 필요하다. 제품이 0개여도 **우측 대시보드는 가려지지 않는다** — 가리는 건 사용자가 스스로 들어온 집중 단계(개별 업로드·분석)뿐. 기존 브랜드는 `cosmetics` 로 보존돼 재질문 대상이 아니다. ⚠️ 어드민이 만든 브랜드와 `/start` 2단계 도입 전 가입자는 여전히 `null` 일 수 있고, **관문이 사라졌으므로 그들은 제품 저장 시점에 위 400 을 만난다**(복구는 디자인 탭 > 브랜드관 서브탭의 셀렉트 한 번). 송장/시딩은 `null` 을 화장품으로 폴백하고 warning 만 남긴다(발급이 막히면 안 되므로). 매핑표는 `klow_server/src/common/constants.ts` 의 `BRAND_CATEGORY_CUSTOMS`(화장품 `Cosmetics`/`3304991000`, 치과재료 `Dental Materials`/`3407002000`) 하나뿐이고, **일반 주문 송장·시딩 송장이 같은 규칙**을 탄다. ⚠️ 제품별 오버라이드는 **없다** — `Product.hsCode`/`customsCategoryEn`·`OrderItem`/`SeedingLink` 통관 스냅샷 컬럼은 전부 **dormant**(빌더가 읽지 않음. 2026-06-19 백필이 전 제품 `hsCode` 를 `3304991000` 으로 박아둬서, 제품값을 우선하면 dental 전환이 먹지 않기 때문). 편집은 klow_brand 스튜디오 **디자인 탭 > 브랜드관 서브탭 > 브랜드 카테고리** + 어드민 브랜드 폼 **취급 품목**. 화장품이 아닌 브랜드는 제품 등록/편집 폼에서 **화장품 카테고리(`categoryKey`) 셀렉트가 숨고** `categoryKey=null` + `category='Dental Materials'` 로 저장된다(klow_web 쇼핑 카테고리 바에는 미노출 — `mist` 선례). 시딩 통관 품명(`SeedingLink.itemName`)도 품목별 후보로 갈리며 **발급 시점에 동결**된다. ⚠️ klow_brand 자동저장은 `useBrandAutoSave.ts` 의 `buildBrandPayload()` **하드코딩 화이트리스트**를 지나므로 새 브랜드 필드는 반드시 거기 등록해야 전송된다. 마이그레이션 `20260730153005_add_brand_category`(ADD COLUMN + DEFAULT) → `20260730160915_brand_category_nullable`(DROP NOT NULL + DROP DEFAULT — 기존 행은 첫 마이그레이션의 DEFAULT 로 이미 `cosmetics` 가 박혀 보존되고, 이후 신규 행만 `null` 로 들어온다). 둘 다 롤링 배포 안전, 백필 없음.

## 시딩 다인원(선착순) 링크 (2026-08)

`SeedingLink.mode`(single|multi) + `maxClaims`(정원 2~500) + `closedAt`(수동 마감). **single = 링크 1개당 1명(기존), multi = 링크 1개로 정원까지 선착순** — 발급 위저드 첫 질문이 방식 선택이고 multi 면 "링크 몇 개" 대신 "최대 몇 명"을 묻는다(링크는 1개만 발급). 신청 단위가 신규 **`SeedingClaim`**(1신청 = 1명 = 1주문 = 1송장)로 빠져 **단일·다인원이 같은 모델**을 쓰고, 브랜드 목록의 발송대기/배송중/시딩기록은 링크가 아니라 **신청자 1명 = 1행**으로 렌더된다(발급/복사 탭만 링크 1행 + `3/10명 신청` 진행 배지·`지금 마감`). 정원의 진실은 **`SeedingClaim` 라이브 COUNT 하나**뿐이고(카운터 컬럼 없음), `reserveSlot()` 이 `SELECT … FOR UPDATE` 로 링크 행을 잠그고 센다 — 만료 예약이 시계만으로 정원에서 빠져 드리프트가 불가능하다. ⚠️ 락 구간은 3왕복까지만 유지하고(동시 신청이 여기서 직렬화된다) Prisma 기본 5초 대신 `SEEDING_TX_OPTS`(20s)를 쓴다. 고객 결제는 체크아웃 진입이 **10분 자리 예약**이며, 정원이 작을 때 이탈 하나가 링크를 얼리지 않도록 **본인 예약 재사용**(게스트 쿠키로 검증한 `resumeOrderId`) + **결제 실패 시 즉시 반납** + TTL 3중으로 막는다. 송장 취소는 그 신청만 취소하고 **자리를 돌려준다**. **중복 신청 차단 (2026-08)**: 정원을 행 수로만 세므로 그것만으론 한 사람이 폼을 반복 제출해 정원을 독식한다 — 같은 링크 안에서 **이메일·연락처·주소 중 하나라도** 겹치면 `422` 로 막는다(비교 대상은 **정원 점유 중인 신청**뿐이라 취소·만료로 자리가 반납되면 재신청도 열린다). 판정은 `reserveSlot()` 의 **행 잠금 안**에서 하고, 그래서 정원 카운트가 `count()` 가 아니라 행 읽기다(한 문장이 행 수와 중복 판정을 겸해 락 왕복 수를 안 늘린다). ⚠️ 그 한 문장은 **`Order` 를 직접 읽고 claim 을 relation 필터로** 쓴다 — `seedingClaim.findMany({ select: { order: … } })` 로 쓰면 Prisma 가 중첩 relation select 를 **2쿼리로 쪼개** 락 구간이 3왕복이 된다(행이 0건이면 1쿼리로 보여 빈 링크 측정에 속는다). 규칙 단일 출처는 `orders/recipient-match.ts` 로 브랜드 발송대기 탭의 중복 수령 **경고**(`attachSeedingDuplicates`)와 원시 정규화를 공유한다(⚠️ 비교 필드는 의도적으로 다름 — 경고는 이름/주소/우편/연락처 각각, 게이트는 이메일·연락처·주소 합성키). ⚠️ **409 가 아니라 422 인 이유**는 klow_web 이 409 를 "선착순 레이스"로 보고 정원 마감 화면으로 넘기기 때문(중복 신청자에게 "정원이 찼습니다"가 오안내된다) — 서버 `code` 규약은 이미 있으나 klow_web `fetchJson` 이 body 를 문자열로 뭉개 못 읽으므로 `code: 'seeding_duplicate_claim'` 은 payload 에 실어만 둔다. 스키마·마이그레이션·백필 없이 `Order` 컬럼에서 즉석 계산하므로 **기존 신청에 자동 소급**. ⚠️ **claim 은 `SeedingLink.countryCode` 를 절대 쓰지 않는다** — 쓰면 첫 신청자의 국가가 링크에 박혀 이후 신청자가 엉뚱한 나라로 발송된다(정본은 `SeedingClaim.countryCode`). 마이그레이션 `20260803081904_add_seeding_claims_multi` 는 추가 전용이라 **롤링 배포 안전**, 백필 `npm run backfill:seeding-claims`(멱등 — **migrate → 백필 → 코드 → 백필 재실행**). 자세히는 [`docs/server/modules/seeding.md`](../server/modules/seeding.md).

## 시딩 통관 신고 수량·신고가 (2026-08-13)

예전엔 `createLink` 가 `SeedingLink.quantity` 를 **1로 하드코딩**해 박스에 몇 개를 담든 EFS 송장 24-9 가 항상 `"1"` 이었다(payload-builder 는 정상이었고 일반 주문은 실수량을 잘 실었다 — 시딩 경로만 고정). 이제 **수량**은 `seeding/seeding-display-name.ts` 의 **`seedingLineQuantity(link, selectedSkus)` 단일 출처**로 갈린다: `selectionMode='brand'` 는 발급 폼의 **박스당 수량**(1~99, `selection.mode==='brand'` 일 때만 스테퍼 노출), `selectionMode='customer'` 는 **바이어가 고른 제품 개수**(`selectedSkus.length` — 링크 `quantity` 는 1로 박히고 무시). ⚠️ **수량은 무게·배송비와 무관**하다(발급 폼 실무게가 이미 박스 단위라 `feeKrw`·캐리어 분기 불변). **신고총액**의 정본은 브랜드 입력이 아니라 **`ShippingCountry.seedingDeclaredValueUsd`**(USD 센트, 어드민 **국가 설정** 탭에서 국가별 면세 한도보다 조금 낮게 세팅)이고, claim 시점에 목적국으로 조회해 **26번 총액으로 고정**(수량 무관), 단가 24-11 은 **`floor(총액 ÷ 수량)`** 로 파생한다 — ⚠️ 반올림이면 총액이 한도를 넘는다(1001÷3 → 334×3 = 1002). 폴백 3단(국가 설정 → 링크 발급 시 `$8.50~$12.50` 랜덤 → 즉석 랜덤)이라 **미설정 국가는 기존 동작 그대로**. ⚠️ `ShippingService.list()` 를 공개(`/v1/shipping-countries`)와 어드민이 **함께 쓰므로** 신고가는 `COUNTRY_SELECT`(공개)가 아니라 **`ADMIN_COUNTRY_SELECT` + `listForAdmin()`** 에만 있다(기본 select 에 넣으면 통관가가 그대로 공개된다. `onlyEnabled` 플래그에 얹지 않은 것도 같은 이유 — 우연한 결합이 깨지면 곧 유출). ⚠️ `ShippingService.update()` 는 **명시적 허용목록**이라 새 필드를 등록하지 않으면 PATCH 가 조용히 무시된다(typecheck 로 안 잡힘). ⚠️ `displayLines()` 는 펼친 행의 `quantity` 를 **이름의 등장 횟수**로 덮는다 — customer 링크는 `OrderItem.quantity` 가 이미 선택 개수라 복사하면 "3줄 × 각 3개 = 9개" 로 제곱이 된다(2026-08-31 이전엔 늘 1이었다. 지금은 중복 이름을 한 줄로 합쳐 EFS 24번과 같은 모양을 낸다 — 아래 `/track` 항목). ⚠️ 유료 checkout 의 **예약 재사용(재진입) 분기가 `OrderItem` 도 다시 써야** 한다 — 안 그러면 "2개 고르고 이탈 → 3개로 재진입"이 옛 수량으로 발송된다. 국가 조회는 기존 `Promise.all`(캐리어·fx)에 얹어 **트랜잭션(정원 락) 밖**에서 끝낸다. 마이그레이션 `GET /admin/shipping-countries/export`(⚠️ `@Get(':iso2')` **앞**에 있어야 `iso2='export'` 로 안 먹힌다) 가 `시딩신고가` 시트에 **전 국가 1행씩**(값은 달러) 내보내고, 고쳐서 `POST /admin/shipping-countries/import/{preview,apply}` 에 기본값 ₩1,000 이 있어 '미설정' 상태가 없다). 라이터·파서 한 쌍은 `shipping/seeding-declared-xlsx.ts` 가 소유하고 회귀 가드는 `__tests__/seeding-declared-xlsx.spec.ts`. 초기 적재는 `npm run seed:seeding-declared-values`(기본 dry-run, `-- --apply`, `--overwrite` 없으면 미설정국만 — 어드민 수동 편집 보존, 멱등) + `prisma/data/seeding_declared_values.json`(각국 **소액면세 한도**만 적고 신고가는 스크립트가 `min(한도−$5, $100)` → $5 단위 내림으로 파생). ⚠️ **de minimis 는 대개 관세 한도이고 부가세는 ## 국내(한국) 시딩 — 브랜드 자체배송 (2026-08-13)

브랜드가 **국내 크리에이터에게도** 샘플을 보낼 수 있게 시딩 배송국에 **대한민국**을 열었다. 국내는 브랜드가 자기 택배를 쓰므로 **EFS 송장을 발급하지 않는다** — `ShippingCarrier` 에 **`DOMESTIC`** 을 추가하고 KR `ShippingCountry` 행(`enabled:false` · `productCarrier:'DOMESTIC'`)을 뒀다. ⚠️ **KR 이 원래 없던 건 코드가 막아서가 아니라 시드 데이터에 없어서**다(KR 은 출발지 `SHIPPER_COUNTRY` 라 요율 엑셀이 전부 수출용). 그 행은 `carriers_by_country.json`(엑셀 산출물)이 아니라 **`prisma/seed/seed-shipping-countries.ts` 의 `DOMESTIC_COUNTRIES` 가 소유**하고 update 절에서도 값을 강제한다 — ⚠️ **마이그레이션에 넣을 수 없다**(Postgres 는 `ALTER TYPE … ADD VALUE` 로 추가한 enum 값을 같은 트랜잭션에서 못 쓰고 Prisma 는 마이그레이션을 트랜잭션으로 감싼다). 한국 claim 도 **진짜 `Shipment` 행을 만들되**(발송대기 조인·발송처리 버튼·중복수령 경고·주문 상태 전이가 전부 이 행을 읽는다 — 없으면 어느 화면에도 안 뜬다) `executeCreate` 가 송화인 검증·payload·EFS 호출을 건너뛰고 바로 `submitted`(`efsTrackingNumber=null`)로 쓴다. 취소도 EFS 를 안 부르고 상태만 되돌리되 **시딩 캐스케이드(주문 취소 + 정원 반납)는 유지**한다. ⚠️ **"송장 발급 후 취소로 발송 기록을 남기는" 방식은 쓰면 안 된다** — `performEfsCancel` 이 시딩 주문을 `cancelled` 로 만들고 정원을 반납해 **발송을 마친 건이 취소됨으로 기록**되고 다인원 링크 자리가 다시 열린다. **브랜드 결제(무료) 링크 전용**이고(`createLink` 가 고객 결제+국내 조합을 400 — 국내는 KLOW 요율이 없고 정산이 EFS 배송완료 코드에 묶여 있어 유료로 열면 조용히 미정산된다), **일반 스토어 체크아웃엔 노출되지 않는다**(`enabled:false`). 브랜드 결제 링크는 국가를 비워 발급하므로 **바이어가 claim 시 한국을 직접 고르고**, 따라서 KR 은 모든 무료 링크의 선택지에 뜬다(링크를 누구에게 보낼지는 브랜드가 정하므로 링크 단위 opt-in 은 두지 않았다). 발송 처리를 누르면 EFS 추적이 없으므로 종착 술어 **`isTerminalShipment`**(EFS=배송완료 코드 / 국내=브랜드 발송 확인)를 통해 기존 `maybeMarkOrderCompleted` 가 주문을 `completed` 로 보내고, 브랜드 화면은 **배송중을 건너뛰고 바로 시딩기록**으로 간다(되돌리기는 대칭). ⚠️ **국내 전용 완료 훅을 따로 만들면 국내·EFS 혼재 주문이 양쪽 어디에도 안 걸려 영영 `shipped` 에 갇힌다** — 술어 한 곳에 두는 게 핵심이다. ⚠️ `ProductCarrierEnum` 에서 **`DOMESTIC` 을 반드시 제외**한다(파생 enum 이라 안 빼면 어드민이 아무 국가나 국내배송으로 바꿔 그 나라 주문이 송장 없이 나간다). ⚠️ `payload-builder` 는 `Record<Exclude<ShippingCarrier,'DOMESTIC'>,…>` + throw 로 **국내 건이 EFS 로 새는 걸 타입으로 차단**한다. `SeedingRate` 요율표 행은 만들지 않고(국내는 KLOW 요율이 없다) `supportedCountries()` 가 교집합 대신 **합집합**으로 국내국을 포함하며 `isDomestic` 플래그를 함께 내린다. 프론트 주의: 발송대기 행의 `selectable`(바코드 인쇄=송장번호 보유)과 `shippable`(발송처리=송장 보유)은 **다른 플래그**이고(합치면 송장번호 없는 국내 건이 발송대기에 갇힌다), 스튜디오 배송 상세의 **EFS 인천 GDC 입고지 안내는 국내 건에서 숨긴다**(안 그러면 브랜드가 박스를 우리한테 보낸다). 마이그레이션 `add_domestic_shipping_carrier` 는 enum 값 추가뿐이라 **롤링 배포 안전**하고 백필도 없지만, 구 인스턴스는 `DOMESTIC` 을 역직렬화 못 하므로 **순서는 마이그레이션 → 코드 배포 → `npm run seed:shipping-countries`** 다. ⚠️ klow_web 에 `ko` locale 이 없어 **한국 신청자는 `/seed` 를 영어로 본다**(별도 과제). 자세히는 [`docs/server/modules/shipments.md`](../server/modules/shipments.md) 국내 자체배송 항목 + [`docs/server/modules/seeding.md`](../server/modules/seeding.md) + [`docs/server/modules/shipping.md`](../server/modules/shipping.md).

## 송장 발급 실패 알림(SMS) + 제한적 자동 재시도 (2026-08-18)

EFS 송장 **자동** 발급 실패가 **완전 무음**이던 것을 고쳤다. ⚠️ **근본 원인은 `executeCreate` 가 EFS 실패를 throw 하지 않고 `status='failed'` row 를 정상 리턴하는 것**이다 — 그래서 결제(`payment.service`)·시딩(`seeding.service`)이 각자 갖고 있던 `createShipmentsForOrderSafe` 의 try/catch 에 **EFS 실패가 애초에 도달하지 않았고**(그 catch 는 송화인 미입력 같은 pre-validation throw 만 잡는다), `ShipmentsService.logger` 는 선언만 되고 한 번도 호출되지 않아 서버 로그에도 흔적이 없었다. 자동 재시도도 **아예 없었다**(큐·cron·attempt counter 전무 — 복구가 100% 어드민 수동 클릭). 이제 **(1) 알림**: 발화의 단일 출처 `ShipmentsService.createForOrderSystem(orderId, reason)` 이 위 중복 래퍼 2개를 합쳐 **반환값의 status 를 직접 검사**하고(절대 throw 안 함), `shipment-alert.service.ts` 가 `SmsService.sendText` 로 **`Admin.shipmentAlertEnabled && phone != null`** 인 어드민에게 문자를 보낸다(**주문 1건 = 문자 1통**, 여러 브랜드 실패는 `Acme 외 2건` 합산). ⚠️ **어드민 수동 발급/재시도는 알림 대상이 아니다**(화면에 `ErrorDetailModal` 이 바로 뜨므로 자기 클릭마다 자기 폰으로 문자가 온다). ⚠️ "이미 전부 발급됨"은 전용 예외 **`ShipmentsAlreadyIssuedException`** 으로 나른다 — 중복 호출에서 정상적으로 나는 예외라 실패로 세면 문자가 스팸이 되는데 **메시지 문자열 비교로 판정하면 문구 한 글자에 깨진다**(어드민 경로는 여전히 같은 문구의 400). **(2) 자동 재시도**: `shipment-retry.cron.ts`(`*/10 * * * *` KST, `SHIPMENT_RETRY_CRON_ENABLED=false` 로만 비활성)가 `retryDue()` 를 부르고 백오프는 **5분→20분→60분**, 상한 3회. ⚠️ **재시도 자격을 `errorMessage` 파싱이 아니라 `executeCreate` 의 두 분기로 가른다** — `efsResult.success===false`(EFS 명시 거부, 재시도해도 동일) → `nextRetryAt=null` / catch 절(네트워크·타임아웃·ack 실패) → 백오프 예약. EFS 회신 문구는 우리가 통제하지 않아 파싱이 언제든 깨지지만 이 축은 구조가 이미 나눠 놓았다. **무한 재시도 방지 3중**: `retryCount<3` · 성공/거부 시 `nextRetryAt=null` · 배치 `LIMIT 20`. ⚠️ **카운터는 호출 前에 올린다**(도중에 죽어도 같은 건을 무한히 다시 집지 않는다). ⚠️ **어드민 수동 `retry()` 는 `retryCount` 를 0 으로 리셋**한다 — 안 하면 3회 소진한 송장은 사람이 원인을 고쳐 준 뒤에도 자동 복구가 영영 안 붙는다. **(3) `pending` 고착 해소**: EFS 호출 중 프로세스가 죽으면 row 가 `pending` 에 남는데 `isReissuableStatus`(failed|cancelled)도 `listPendingGroups`(pending 제외)도 못 잡아 **어느 화면에도 안 뜨고 재발급도 못 하는 고아**가 됐다 — `retryDue()` 가 `updatedAt < now−30분` 인 pending 을 `failed`+`nextRetryAt=now` 로 승격해 **기존 재시도 경로가 주워 가게** 한다(⚠️ 전용 복구 경로를 따로 만들면 국내배송 완료 훅 때처럼 사각지대가 생긴다). **어드민 전화번호**는 `Admin.phone`(digits-only, 검증은 `common/validation/shared.ts` 의 `KrPhone` — 브랜드 전화 OTP 와 **공유**하려고 `brand-auth.ts` 에서 올렸다)이고 편집은 `/admins` **프로필 수정 모달**(SuperAdminGuard)이며, 수신 대상 토글은 출고관리 **'실패' 탭**(`GET|PUT /admin/shipments/alert-recipients`, **AdminGuard** — super 전용이면 operator 가 자기 화면 설정을 못 본다). ⚠️ 두 라우트는 **`@Get(':id')` 앞**에 둬야 한다(`shipping-countries/export` 선례). ⚠️ zod `phone` 에 **`.default()` 금지** + `updateProfile()` **명시적 허용목록** 등록 필수(빠뜨리면 PATCH 가 조용히 무시된다). ⚠️ `setRecipients` 는 **번호 없는 어드민을 400 으로 거절**한다("체크는 켜져 있는데 아무에게도 안 가는" 상태 = 지금 고치려는 무음 실패와 같은 병). 수신자 변경(`PUT`)은 **SuperAdminGuard** 다 — 읽기만 AdminGuard(operator 가 현황은 봐야 한다). 쓰기까지 열면 operator 가 남의 `Admin` 행을 고칠 수 있는 첫 경로가 생기고, 그 권한으로 **전원 수신을 꺼버릴 수 있다**(이 기능이 막으려는 무음 상태로 그대로 되돌아간다). 마이그레이션 `20260818100637_add_admin_phone_and_shipment_retry` 는 **추가 전용 → 롤링 배포 안전 · 백필 없음**. ⚠️ 새 cron 이라 `test/app.e2e-spec.ts` 기대 목록이 **7개**로 늘었다. 회귀 잠금은 `shipments/__tests__/{shipment-retry,shipment-alert}.spec.ts`. 배포 순서는 **klow_server → klow_admin**이고, **배포 직후 `/admins` 에서 번호를 채우고 실패 탭에서 수신자를 체크해야 실제로 문자가 간다**(둘 중 하나라도 비면 조용히 아무에게도 안 간다). 자세히는 [`docs/server/modules/shipments.md`](../server/modules/shipments.md) + [`docs/server/modules/admin-auth.md`](../server/modules/admin-auth.md).

## EFS 31번 세금식별코드 — 국가별 규칙 테이블화 + 멕시코(MX) RFC (2026-08-18)

멕시코 세관이 수취인 **RFC**(Registro Federal de Contribuyentes)를 통관 요건으로 요구해 결제·시딩 폼에서 받기 시작했다. ⚠️ **새 기능이 아니라 기존 CN 전용 구현의 일반화**다 — 31번 슬롯은 이미 `Order.recipientTaxId`(`VarChar(20)`) → `payload-builder` 31번으로 연결돼 있었고 빌더는 국가를 안 보고 컬럼을 그대로 흘린다. 그래서 **마이그레이션도 백필도 없다**(RFC 13자 < 20). 막고 있던 건 **`recipientTaxId` 의 `regex(CN_RESIDENT_ID)` 가 국가 무관하게 zod 필드 레벨에 박혀 있던 것** 하나로, 멕시코 RFC 가 무조건 400 이었다(같은 선언이 `order.ts`×2 + `seeding.ts`×2 로 4벌 중복). 이제 정본은 **`common/validation/shared.ts` 의 `TAX_ID_RULES`** 한 곳 — `{pattern, maxLength, required, message, missing}` 이고 CN = 거민신분증 18자리, MX = RFC `^[A-ZÑ&]{3,4}\d{6}[A-Z0-9]{3}$`(법인 12 / 개인 13자, 미등록 개인은 제네릭 `XAXX010101000` / 외국인 `XEXX010101000`). ⚠️ **필드 스키마엔 정규식을 두지 않는다** — 국가마다 형식이 달라 필드 레벨 정규식은 배송국이 바뀌는 순간 오탐이 된다. ## 카페24 자사몰 연동 — OAuth 실왕복 + 토큰 갱신 직렬화 (2026-09-23)

브랜드가 자사몰(카페24)을 OAuth 로 연결해 주문을 불러오고 [3PL 출고신청](#2026-09-22)으로 전환하는 축의 **연동 절반**이 들어왔다(상품 매핑 CRUD 포함). ⚠️ **주문 불러오기·전환은 아직 없다** — 그쪽은 `/catalog`·`import`·`convert` 이고 계획 문서 §8 의 3-2·4-1·4-2 다. 설계 정본은 [`plan/cafe24-fulfillment/implementation-plan.md`](../plan/cafe24-fulfillment/implementation-plan.md), 모듈 문서는 [`server/modules/cafe24.md`](../server/modules/cafe24.md). 2026-09-23 테스트 몰 `simsgood1` 로 **OAuth 왕복이 실제로 통과했다**(연결 → `connected:true` → 해제 → `connected:false`, lazy refresh, 동시 요청 경합, 주문 API HTTP 200). ⚠️⚠️ **여기서 나온 가장 비싼 실측은 만료 시각 문자열이다** — 카페24가 `expires_at: "2026-09-23T19:16:43.000"` 처럼 **타임존 표기 없이** 주고 값은 **KST 벽시계**다. 타임존 없는 ISO 문자열을 `Date.parse` 에 그냥 넘기면 **서버 로컬 시각**으로 읽히는데, **개발 맥북은 로컬 TZ 가 KST 라 우연히 맞고 운영(Railway·Docker)은 UTC 라 9시간 늦게 읽는다** — 즉 **로컬에서는 영원히 재현되지 않고 운영에서만 터지는** 형태다(이미 죽은 토큰을 살아 있다고 믿고 호출해 401). 그래서 `parseCafe24Expiry` 가 **표기가 없으면 `+09:00` 을 붙인다**. ⚠️ 기존의 "폴백의 2배를 넘으면 버린다" 범위 검사는 **안전망일 뿐 주 방어가 아니다** — 실측상 access 는 그게 잡아주지만(2시간짜리가 11시간으로 읽혀 4시간 상한 초과) **refresh 는 14일+9시간이 28일 안이라 그대로 통과한다.** 회귀 스펙(`cafe24/__tests__/cafe24-expiry.spec.ts`)은 기대값을 **`Date.parse` 가 아니라 절대 인스턴트**(`Date.UTC(...) - 9h`)로 적는다 — `Date.parse` 로 만들면 스펙이 버그와 **같이 틀려서 통과**한다. ⚠️ 이 `+09:00` 은 **개발자센터 앱 설정의 Time zone(`Asia/Seoul`)과 묶여 있고**, 그 설정은 만료 시각뿐 아니라 **주문 조회 날짜 축에도** 걸린다(그래서 서버(UTC)에 맞추는 대신 KST 를 유지했다 — 주문 날짜가 훨씬 자주 쓰이고 착오 비용이 크다). **토큰 갱신은 `cafe24-token.ts` 가 직렬화한다.** ⚠️⚠️ 카페24는 갱신할 때 **refresh token 도 함께 회전**시켜서, 두 요청이 동시에 갱신하면 한쪽이 **이미 죽은 토큰으로** 요청해 연동이 **영구 실패**한다. 레포에 advisory lock 이 0건이라 `SELECT … FOR UPDATE` 를 쓰고(`fulfillment`·`seeding`·`brand-auth` 선례), **`NOWAIT` 을 쓰지 않는다**(두 번째 요청은 실패가 아니라 기다렸다가 다시 봐야 한다). ⚠️ **락을 얻은 뒤 만료를 다시 확인하는 그 한 줄이 회전 무효화를 막는 유일한 지점**이고, UPDATE 는 access·refresh·만료 2개를 **한 문장**으로 쓴다(나눠 쓰면 중간에 죽었을 때 refresh 만 새것이 되어 다음 갱신이 영구 실패). 낙관적 버전 컬럼은 **일부러 안 쓴다** — 충돌한 쪽이 재시도하면 이미 회전된 토큰으로 또 요청해 쿼터만 태운다. 실측 검증: 만료를 과거로 돌린 뒤 **동시 요청 2개 → 둘 다 성공 · 같은 토큰 · 회전 1회**. ⚠️ **실패 처리가 갈린다** — **4xx = 복구 불가 → `needsReauth=true`**(브랜드에게 "다시 연결해 주세요"를 띄우는 유일한 신호), **5xx·네트워크 = 일시 장애 → 연동을 건드리지 않는다**(카페24 쪽 장애로 멀쩡한 연동을 죽이면 브랜드가 쓸데없이 재연동한다). 신규 cron **`cafe24-token-refresh`**(매일 KST 03:00, refresh 만료 **3일 이내**를 미리 굴림, cron **10 → 11**) — ⚠️⚠️ 이게 없으면 **2주를 쉰 브랜드는 재연동해야 한다**(refresh 수명 14일인데 갱신은 쓸 때만 일어난다). 창을 하루로 줄이면 cron 이 한 번 실패한 날 그 연동이 그대로 죽는다. **개발자센터 쪽 실측 셋.** ⚠️⚠️ **Redirect URI 에 `http://localhost` 를 등록할 수 없다** — HTTPS 전용이고 IP 도 거부한다. 이 레포의 다른 연동(`GOOGLE_*`·`META_*`)은 전부 localhost 를 등록해 두고 로컬에서 왕복을 돌리므로 **그 관례를 복사하면 착수 시점에 막힌다**(로컬 OAuth 에는 cloudflared/ngrok 같은 HTTPS 터널이 필요하고, 터널 주소가 바뀌면 개발자센터 목록과 `CAFE24_BRAND_CALLBACK_URL` 을 **함께** 고쳐야 한다 — 한 글자만 달라도 토큰 교환 실패). **주문 조회 기간 상한은 3개월**(92일 요청이 422, 31일은 200)이라 우리 쪽 14일 상한은 그 안이다. 쿼터 헤더는 **`x-api-call-limit: 4/40`**(소문자)이고 429 는 502 로 접지 않고 그대로 흘린다 — 502 면 사용자는 "실패"로 읽고 **더 누르는데** 그게 정확히 상황을 악화시킨다(⚠️ `Retry-After` 는 **미검증** — 429 를 실제로 맞아 본 적이 없다). ✅ **심사 요건에 "앱 실행 화면(iframe)"이 없다** — 제출물은 스토어 리스팅(이름·아이콘·설명·스크린샷·FAQ·가격)뿐이고, 더구나 App URL 의 기본 실행 방식이 **`New window`(iframe 아님)** 라 `klow_brand_sid` 가 1st-party 로 전송된다. 그래서 "v1 은 앱스토어 진입 미지원"이라는 회피안이 유지된다(계획 문서 §7 R1). ⚠️⚠️ **주문 상태 코드는 아직 한 번도 못 봤다** — 테스트 몰에 3개월간 주문이 0건이라 §2 B 가 비어 있다. **4-1 착수 전에 테스트 주문을 넣고 실측할 것. 추측해서 상수로 박지 말 것.** 상품 매핑(`Cafe24ProductMap`)은 카페24 **(상품번호, 옵션) → KLOW 제품**이고 ⚠️⚠️ **`POST` 는 보낸 줄만 반영한다(`PUT` 이 아니다)** — 몰 상품이 수백~수천 개라 매핑 화면이 반드시 페이지를 끊는데, 전체 교체 규칙이면 한 페이지 저장이 **나머지 페이지의 매핑을 전부 지운다**(`BrandInventoryInput` 과 같은 규칙). ⚠️ 저장은 **`productId` 의 브랜드 소유권을 검사**한다 — 남의 제품에 매핑하면 전환 시점에 **다른 브랜드의 창고 재고가 차감되고**, 매핑 자체는 조용해서 사고가 한참 뒤 출고신청에서 드러난다. **N:1 을 허용**하므로(옵션 여럿 → 같은 제품) 전환이 `productId` 기준으로 **수량을 합산**해야 한다(안 하면 `FulfillmentRequestInput.items` refine 이 400). 옵션 없음은 **빈 문자열**이다 — null 이면 Postgres 에서 NULL 끼리 같지 않아 `@@unique` 가 중복을 못 막는다. ⚠️ **`Cafe24Connection.defaultCountryCode` 가 없으면 비-KR 몰의 주문이 전부 `KR` 로 창고에 나간다** — 카페24 주문에는 국가 칸이 없고 `FulfillmentRequestInput.countryCode` 는 ISO2 필수라 어딘가에서 정해야 하는데 그 자리가 이 컬럼이다(DB 기본값 `KR` 은 마이그레이션용이지 "브랜드가 고른 값"이 아니다). 연결 **후에도** 바꿀 수 있어야 해서(몰 운영국이 바뀐다) `/connect` 쿼리가 아니라 `PATCH /connection` 이고, 바뀐 값은 **다음 전환부터** 적용된다(이미 만들어진 출고신청은 창고로 나간 송장이라 소급하지 않는다). ⚠️ 검증 스키마는 `common/validation/shared.ts` 의 `Iso2Code` 로 `FulfillmentRequestInput` 과 **같은 정의**다 — 갈리면 한쪽만 통과한 값이 전환 시점에 400 이 되고 그때는 브랜드가 이미 주문을 골라 놓은 뒤다. 곁들여 **출고신청 목록의 기간 필터를 서버로 옮겼다**(구 `REQUEST_TAKE = 200` — 화면이 상한 안에서 클라 필터를 걸어, 카페24 유입이 켜지면 몇 주 만에 상한을 넘고 넘는 순간 오래된 건이 **조용히** 사라지며 상태 칩 건수까지 거짓말을 했다). `since`/`until` 은 KST 달력일이고 `until` 은 **그날 끝까지**(반열림), **상태별 건수는 기간만 건 모집단**에서 서버가 센다(상태로 또 좁히면 칩 하나를 고르는 순간 나머지가 0). ⚠️ 그 두 칸을 공용 `FulfillmentListQuery` 가 아니라 **브랜드 전용 스키마**에 넣었다 — 어드민 스키마가 그걸 extend 해서, 공용에 넣으면 어드민이 **받고도 쓰지 않는 필드**가 생긴다(settlement·shipping-rates 의 미작동 반쪽 구현 재현). 같은 이유로 재고 화면의 `출고 대기` 합계도 서버 `groupBy`(`outboundPending`)로 옮겼다. 상한은 없애지 않고 **보이게** 했다 — `total > items.length` 면 "최근 200건만 표시했어요"를 띄운다. 마이그레이션 `20260923052254_add_cafe24_fulfillment`(`CREATE TABLE` ×4 · `CREATE TYPE` ×1 · `ADD COLUMN` ×1 · **DROP 0건 · 백필 없음** → 롤링 안전), 라우트 **361 → 369**, cron **10 → 11**. ⚠️ FK 동작 셋이 핵심이다 — `Cafe24ProductMap.productId` **Cascade**(기본 `Restrict` 면 매핑 걸린 제품 삭제가 P2003 = 기존 기능 회귀) · `Cafe24Order.fulfillmentRequestId` **SetNull**(Brand 삭제 캐스케이드 순서를 PG 가 보장하지 않는다) · `Cafe24OrderItem.productId` **SetNull**(스냅샷 캐시). ⚠️⚠️ **`mallId` 는 SSRF 벡터**라 방어가 **두 겹**이다 — zod(입력 경계)와 `cafe24ApiOrigin()`(조립 경계). 후자가 정규식을 **다시** 도는 이유는 `..` 이 `https://...cafe24api.com` 을 만들어 hostname 검사만으로는 통과하기 때문이고, 전자가 따로 있는 이유는 DB 값·쿠키가 zod 를 거치지 않고 들어오기 때문이다. **한 겹만 남기지 말 것**(`__tests__/cafe24-ssrf.spec.ts` 가 둘을 따로 검사한다 — tsc 도 e2e 도 이걸 못 잡는다). ⚠️ 한 몰이 두 브랜드에 물리면 **409 + 로그**다 — `instagram.service.ts` 의 `deleteMany`(이전 연동 삭제)를 복제하지 않았다. 그쪽 근거는 *"그 계정으로 OAuth 로그인했다는 것 자체가 통제권 증명"* 인데 **자사몰은 법인 자산이라 그 논거가 성립하지 않고**, 겹치는 것 자체가 사고 신호다. 토큰 암호화 키는 `CAFE24_TOKEN_ENCRYPTION_KEY` **전용**이다 — ⚠️⚠️ `META_TOKEN_ENCRYPTION_KEY` 를 재사용하면 Meta 키를 돌리는 순간 카페24 토큰이 전부 안 읽힌다(crypto 유틸이 세 번째 복사본인 것은 **의도된 격리**). 배포는 **3PL 과 한 번에** 낸다(계획 문서 §1-A · §8 6단계) — 마이그레이션 2개를 순서대로 적용하고 **3PL 왕복을 먼저 통과시킨 뒤** 카페24를 켠다.
