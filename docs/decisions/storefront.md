## 프로모션(구 캠페인) = 인플루언서 "할인가 브랜드관 링크" 전환 (2026-08-17)

이 기능이 어필리에이트 추적 도구에서 **브랜드가 제품×국가별 판매가를 직접 정하는 할인 링크**로 바뀌었다. 발급 모달은 이제 **이름 + 제품별·국가별 판매가**만 받는다(SNS 플랫폼·계정주소·메모 입력 제거). 저장 정본은 신규 **`PromotionProductPrice(promotionId, productId, iso2, priceLocal)`** — 값 모양은 `ProductOnsiteCountryPrice` 와 동일(현지통화 major·non-null·상속 국가는 행 없음)하고 프로모션 단위 **replace-all** 이다. 구 `Promotion.{snsUrl,platforms,countries,discountPct,memo}` 5컬럼 + `PromotionPlatform` enum 은 **드롭**했고 기존 할인 데이터는 백필 없이 버렸다. ⚠️⚠️ **병합 규칙이 바뀌었다 — 프로모션 세일가가 국가 핀·국가 할인을 outright 이긴다(`max` 아님).** 구 모델은 `max(국가할인%, 프로모션할인%)`(고객 유리)였지만 이제 브랜드가 금액을 명시 지정하므로 그 값이 정본이고, 취소선은 프로모션 전 정상가를 그대로 쓰며 표시 할인율은 `round((1−청구가/정상가)×100)` 로 파생한다(세일가가 정상가보다 비싸면 **0 클램프** — 음수 % 방지). ⚠️ **세일가를 안 정한 제품은 정상가로 그대로 노출**된다(브랜드관은 전 제품을 계속 보여준다) — 매칭 키가 `brandId` 가 아니라 `productId` 라 `PromotionPricing` 에서 brandId 를 아예 뺐다. ⚠️ **`PricingRow.id` 를 필수로 올렸다** — optional 이면 id 를 빠뜨린 select 가 컴파일을 통과하고 런타임에 "조용히 프로모션 미적용"으로 떨어진다(가격 사고는 조용할수록 나쁘다). ⚠️⚠️ **같은 작업에서 실재 과청구 구멍을 고쳤다**: `orders.service.billingRate` 가드가 국가 핀만 보고 있어서, FX 미해결국에 프로모션 세일가가 있으면 폴백 `rate=1` 로 `¥3,000` 이 **`$3,000` 으로 청구**될 수 있었다 — 가드를 `modules/orders/billing-rate.ts` 로 빼고 `promotionPriceLocal` 인자를 추가했다(현지통화로 해석되는 입력이 늘면 **반드시** 여기 인자로 추가할 것). ⚠️ zod PATCH `prices` 는 **`.optional()`** 이다 — `.default([])` 면 배포 창의 구 klow_brand 탭이 `{status}` 만 보내도 세일가 전체가 조용히 지워진다(`onsiteDiscountPct` 선례). ⚠️ `updateForBrand` 는 세일가만 보낼 때 스칼라 update 가 비어 `updateMany.count` 로 스코핑을 못 하므로 **소유 검증을 `findFirst` 로 먼저** 한다. 조회는 목적국으로 좁힌 **1회**(`prices: { where: { iso2 } }` — 20제품×98국 중 ~20행)이고 `resolvePricingCtx` 는 `onsite:true` 면 쿼리조차 안 쏜다(현장은 프로모션 무관, 구조적으로도 `onsitePriceLine` 이 세일가를 인자로 안 받는다). 정산은 실청구가 역산이라 **할인분이 자동으로 브랜드 부담**. 구 단축링크 **`/r/{code}` 는 컨트롤러째 제거**(302 가 code 를 버려 할인이 애초에 안 걸렸고 브랜드 UI 에도 없었다) — 유입 경로는 pretty 링크 하나다. klow_web 브랜드관 카드에 **`-N%` 칩**을 붙였다(취소선만 있던 유일한 화면). 브랜드 UI 는 `PromotionPriceEditor`(제품 목록) → `PromotionPriceModal`(국가별 입력) 두 컴포넌트이고 **스튜디오 `PriceModal` 이 아니라 현장(onsite) 탭이 템플릿**이다(할인 슬라이더·무료배송·박스규격이 프로모션엔 없다). 프리필은 **할인 전 정가**이고 국가 할인 중인 나라엔 "평소 −N% 적용가"를 병기한다(안 그러면 브랜드가 프로모션 방문자 가격을 실수로 **올린다**). ⚠️ **알려진 갭**: `cart.service` 는 프로모션 code 없이 가격을 매겨 **로그인 서버 카트만 정상가**를 보여준다(청구 정본은 quote). 마이그레이션 `campaign_product_prices` 는 CREATE TABLE + **DROP COLUMN/TYPE 이라 롤링 배포 비안전**(단일 레플리카 컷오버) — 2단계 분할도 불가하다(`snsUrl` 이 default 없는 NOT NULL 이라 신 서버가 INSERT 를 못 한다). 배포 순서는 **(관대화 선행 배포) → klow_server 컷오버 → klow_brand → klow_admin → klow_web**. 회귀 잠금은 `pricing/__tests__/promotion-pricing.spec.ts`(병합 규칙·0 클램프·현장 무관·표시가==청구가) + `orders/__tests__/billing-rate.spec.ts`. 자세히는 [`docs/server/modules/promotions.md`](../server/modules/promotions.md).

## campaign → promotion 전면 rename (2026-08-18)

위 항목의 기능을 **이름만** 바꿨다(동작·계약 로직 무변경). ⚠️ **이유는 취향이 아니라 용어 충돌**이다 — `SeedingLink.campaignName`(시딩 발급 배치 라벨)이 이미 "캠페인"을 쓰고 있어, 브랜드 화면에 **"시딩 캠페인"과 "할인 캠페인"이 서로 다른 탭에서 같은 단어로** 공존했다. ⚠️⚠️ **`campaignName`·그 주변 시딩 식별자는 rename 대상이 아니다** (일괄 치환하면 시딩 코드까지 끌려간다 — 실제로 한 번 끌려가서 되돌렸다). 바뀐 것: 테이블 `Campaign`/`CampaignProductPrice`/`CampaignDailyStat` → `Promotion*`, 컬럼 `*.campaignId` → `promotionId`(**`Order` 포함**), enum `CampaignStatus` → `PromotionStatus`, 모듈 `src/modules/campaigns/` → `promotions/`(파일 5개), `src/pricing/campaign.ts` → `promotion.ts`, `common/validation/campaign.ts` → `promotion.ts`, 라우트 `/admin/campaigns`·`/v1/brand/campaigns`·`/v1/campaigns/track` → `promotions`, 공개 쿼리 `?campaign=` → `?promotion=`, 주문·견적 body `campaign` → `promotion`, 어드민 탭 `/campaigns` → `/promotions`(라벨 "프로모션"), klow_brand 탭 `/campaigns` → `/promotions`(**UI 라벨은 "할인 링크"** — 코드·주석의 도메인 용어 "프로모션"과 의도적으로 다르다). ⚠️ **같은 날 "인플루언서 전용" 전제도 걷어냈다** — 받는 사람은 검색과 `CuratedInfluencer` 는 진짜 인플루언서 전용이라 무관). **안 바뀐 것**: 공개 유입 링크 `klow.kr/{brand.slug}/{promotion.slug}`(배포된 링크가 그대로 살아있다), `Promotion.code` 값, 저장 데이터 전부. ⚠️ 마이그레이션 `20260818021500_rename_campaign_to_promotion` 은 **`ALTER … RENAME` 만** 쓰는 순수 rename(데이터 이동·손실 0, **롤링 배포 비안전** — 구 서버가 옛 이름을 못 찾으므로 단일 레플리카 컷오버)이고 **인덱스·제약 이름까지 함께 바꾼다**(안 바꾸면 Prisma 가 드리프트로 보고 rename 마이그레이션을 또 만든다). ⚠️⚠️ **이 마이그레이션은 손으로 썼다 — `prisma migrate dev` 는 model rename 을 감지하지 못하고 DROP TABLE + CREATE TABLE 을 생성해 라이브 링크와 `Order` 귀속을 통째로 날린다.** CLAUDE.md 의 "수동 SQL 파일 생성 금지" 규칙에 대한 **의도적 ## 브랜드관 통계에 판매 분석(국가·제품) + 현장 채널 추가 (2026-08-19)

아래 두 항목의 퍼널이 `방문자 → 장바구니 → 결제` 까지 왔지만 **어디서·무엇이 팔렸는지**는 여전히 어디에도 없었고, 부스(현장) 실적은 정산 화면에만 있었다. klow_brand `/stats` 를 **채널 탭 `[전체][일반][할인링크][현장]` + 기간 `[7][30][90][전체]`** 구조로 바꾸고 국가·제품 랭킹(가로 막대 TOP 5 + 전체 보기)을 붙였다. ⚠️ **신규 수집이 0건이다** — 국가는 `Order.countryCode`(온라인=배송국 / 현장=손님이 고른 **가격 기준국**), 제품·수량은 `OrderItem` 에 이미 있어 **과거 주문까지 즉시 소급**된다(방문·담기는 영원히 소급 불가라 이 비대칭이 아래 모든 결정의 근원이다). 마이그레이션·백필·klow_web 변경 없음, cron 개수 불변(8). ⚠️⚠️ **한 화면에 모집단이 둘이 산다.** 퍼널 = `BrandDailyStat`(브랜드관을 거친 방문자 · 현장 제외 · 환불 미차감 · 방문일 버킷 · **명**), 판매 분석 = `Order`/`OrderItem`(결제 완료 전 주문 · `/shop`·검색·자사몰 유입과 현장 포함 · 환불 제외 · `paidAt` 버킷 · **건/개**). 같은 탭의 "결제 48명"과 "국가 합계 63건"은 **서로 다른 숫자이고 그게 정상**이라, 두 섹션에 모집단 한 줄 설명을 상시 노출한다 — **그 문구를 지우면 브랜드에겐 그냥 숫자가 틀린 화면이 된다.** ⚠️ **채널의 정의도 퍼널과 다르다** — 퍼널 `source` 는 *그 방문자의 그날 첫 진입 경로*, 판매 채널은 *주문의 성질*(`onsite` > `promotionId≠null` > `direct`)이다. 할인 링크로 들어왔지만 체크아웃까지 code 가 안 따라간 주문은 퍼널에선 promotion, 랭킹에선 direct 다. 억지로 맞추려면 방문 원장과 주문을 조인해야 하는데 그 순간 랭킹이 퍼널 모집단으로 쪼그라들어 이 기능의 목적이 사라진다. ⚠️ **현장은 방문·담기를 여전히 수집하지 않는다**(POS 흐름 + 공용 태블릿이 순방문을 1로 누른다 — 아래 항목의 판단 유지). 그래서 현장 탭은 3칸을 `'—'` 로 비우지 않고 **칸 구성 자체가 다르고**(결제 건수·판매 수량·판매 제품 종수 + 주문 기준 `건` 추이 1개) **전환율이 없다**. 신규는 `GET /v1/brand/storefront-stats/sales?days=` 하나(`storefront-sales.service.ts`)이고 **채널별 raw 행을 한 번에** 내려 **탭 전환에 재요청이 없다**(`전체` 는 클라 합산 — 한 주문은 정확히 하나의 (채널, 국가)라 중복이 없다). ⚠️⚠️ **`summary` 를 서버가 함께 내는 건 편의가 아니라 오집계 방지다** — 한 주문에 그 브랜드 제품이 2종이면 `products` 행에 2번 나타나므로 화면이 제품 행을 더해 건수를 만들면 부풀려진다. 건수는 `countries`(또는 `daily`)에서만 나올 수 있고, 그 규칙을 주석이 아니라 **응답 모양으로 강제**했다(화면엔 더할 것이 남아 있지 않다). `all.productCount` 도 채널별 합이 아니라 distinct 다. ⚠️ 일자 버킷 SQL 은 **`AT TIME ZONE 'UTC' AT TIME ZONE 'Asia/Seoul'` 이중 캐스트**(한 번만 걸면 00~09시 KST 결제가 전날로 밀린다 — `kstWeekBucketSql` 과 같은 함정). ⚠️ 국가명은 **서버가 `ShippingCountry.nameKo` 를 하한(`statsWindowStart`)도 같은 상한만큼** 거슬러 가야 한다(하한 없이 뽑고 창만 자르면 국가 합계에 창 밖 주문이 섞인다). ⚠️ 어드민 라우트는 `'all'` 을 **일부러 안 받는다**(`StorefrontAdminStatsQuery` 분리 — 브랜드 스키마를 그대로 쓰면 `'all'` 이 문법상 통과하며 조용히 오늘 하루만 ## 브랜드관 방문 통계 + 장바구니 전환 (2026-08-19)

타입 재생성 필요 + 과거 행이 참조). 브랜드관을 렌더하는 라우트는 정확히 3개(`/{slug}` · `/{slug}/{promotionSlug}` · 레거시 `/brand/{id}`)이고 읽는 쿼리는 `mode=onsite` 하나뿐이다(브랜드가 공유한 `/product/{id}?brand=` = **PDP** 딥링크도 2026-08-20 부터 방문으로 클라에 맡기지 않는다** — 클라는 불투명 `visitorId`(localStorage 난수)만 보내고 API 에 `unique` 필드가 **아예 없다**. 클라가 계산하면 (a) 진실을 주장하게 되고 (b) 더 중요하게 **"방문한 그 사람이 담았는가"를 서버가 알 수 없어 퍼널이 성립하지 않는다**. 저장소를 못 쓰면(프라이빗 모드) **트래킹을 통째로 건너뛴다** — 매번 임시 id 를 만들면 순방문이 방문수까지 부풀어 오른다. ⚠️⚠️ **담기는 그날 그 브랜드관을 방문한 사람의 담기만 센다**(원장 행이 없으면 아무것도 기록 안 함) — 이게 퍼널 정의 그 자체이고, 덕분에 **`uniqueCartAdds ≤ uniqueVisits` 가 구조적으로 보장**돼 전환율에 클램프가 필요 없다(클램프는 정의가 틀렸다는 신호를 숨길 뿐이다). 귀속은 담기 시점 URL 이 아니라 **그 방문자의 그날 첫 진입 경로**다. ⚠️ `recordCartAdd` 는 `led.carted` 를 **update 前에 값으로 붙잡는다**(뒤에 읽으면 순담기자가 영원히 0). ⚠️ **brandId 는 서버가 `productId` 로 해석**한다 — 공개 제품 응답엔 `brandId` 가 없고(`StrippedPricingKeys` 가 의도적으로 벗긴다) 그 목록도 `CartLine`(persist+migrate 영속 스키마)도 건드리지 않았다. 담기 초크포인트는 `useCartStore.addToCart` 의 `addQty <= 0` early return **바로 다음** — 그 가드가 "브랜드당 5개 상한에 막힌 ## 제품 상세(PDP) 직접 진입도 방문 통계에 집계 (2026-08-20)

브랜드 피드백 — **"브랜드관으로 들어가야만 집계된다."** 방문 비콘이 `BrandStorefront` 한 곳에서만 나가서, 브랜드가 자사몰·SNS 에 붙인 **`/product/{id}?brand={slug}`(PDP) 링크 유입이 통계에서 통째로 사라지고 있었다** — 방문뿐 아니라 **담기·결제까지**. 담기 게이트가 "그날 원장 행이 있을 때만"이고 `Order.visitorId` 도 방문 비콘이 만든 토큰에 달려 있어서, 브랜드가 자기 돈으로 붙인 유입 채널의 성과가 `/stats` 에서 **전부 0** 으로 보였다. ⚠️ **게이트는 `?brand=` 유무 하나**다 — `/shop`·검색을 둘러보다 스쳐간 조회는 안 센다(PDP 가 국가 선택 모달에 이미 쓰는 조건 `useGuestCountryPrompt(brandMode && …)` 과 **같은 잣대**). ⚠️ **새 `source` 값을 만들지 않고 기존 `direct`(일반)에 합쳤다** — 그 덕에 prisma enum(`ALTER TYPE ADD VALUE`)·`REPORTED_SOURCES`·응답 shape·klow_brand `ChannelTabs`/`StorefrontStatsBoard`·klow_admin 이 **전부 무변경**이고 **마이그레이션도 없다**(새 source 를 `REPORTED_SOURCES` 에 넣었다면 `totals.all` 정의가 바뀌어 어드민의 "일반 X · 할인 링크 Y" 줄이 합계와 어긋났을 것이다). ⚠️⚠️ **귀속 키는 `productId` 이고 URL 의 `?brand=` 슬러그가 아니다** — 슬러그는 주소창에서 바꿀 수 있어 `/product/{A사 제품}?brand={B사}` 로 **남의 방문수를 부풀리는 통로**가 된다. 슬러그는 **클라의 게이트로만** 쓰고 서버가 `Product.brandId` 로 해석한다(담기 비콘과 같은 3줄 — PDP 는 brandId 를 알 수 없다. 공개 제품 응답을 `StrippedPricingKeys` 가 벗긴다). zod 는 `brandId ⊕ productId` 를 **`superRefine`** 으로 강제한다(`z.union` 은 400 바디에 중첩 `unionErrors` 를 통째로 싣는다 — issue 1개가 낫다). 라우트는 **추가하지 않았다**(같은 이벤트라 집계 경로가 하나여야 하고, 나누면 klow_web 도 dedupe 를 두 벌 든다). ⚠️ **`track/country` 도 함께 넓혀야 한다** — 딥링크 유입은 첫 방문이라 **국가가 null 인 채로 도착하는 게 가장 흔한 경로**이고, 안 넓히면 그 방문의 국가가 거의 전부 '미상'으로 남는다. ⚠️ 브랜드관 그리드의 상품 링크에도 `?brand=` 가 붙어 **임베드 URL 과 형태가 같다**(구별 불가) → klow_web 모듈 레벨 **`visitedBrands`** 로 "그 탭에서 그 브랜드를 아직 안 봤을 때만" PDP 방문을 센다. **순방문(명)·전환율은 이 가드가 없어도 정확하다**(원장 유니크 제약이 `uniqueVisits: 0` 을 만든다) — 가드가 지키는 건 `visits`(회)의 의미와 요청 수뿐이니 새 탭·새로고침 누수를 sessionStorage 로 더 메우려 들지 말 것. 슬러그는 `.trim().toLowerCase()` 로 비교한다(브랜드관은 DB 정본 소문자, PDP 는 URL 원문이라 대문자 URL 하나에 가드가 뚫린다). ⚠️⚠️ **담기가 방문 비콘을 기다린다(`pendingVisit`)** — 딥링크 PDP 는 담기 버튼이 활성화되는 순간이 방문 POST 를 쏘는 순간과 거의 같아서, 안 기다리면 담기가 원장 행보다 먼저 도착해 서버가 버린다(**이 기능이 살리려던 바로 그 담기**). `.then(send, send)` 로 실패도 태운다. 언로드 유실은 없다(담기 후 이동이 전부 `router.push`). **국가 비콘도 같은 `afterVisit` 로 줄 선다 (2026-08-21)** — 국가가 방문을 앞지르면 서버가 원장 행을 못 찾아 버리는데 클라는 이미 dedupe 에 찍어 재시도가 없다(로그인 손님의 `useSessionSync` → `syncCountry` 에서 실제로 난다). ⚠️⚠️ **국가 dedupe 의 축은 `productId` 가 아니라 브랜드 문맥이다 (2026-08-21 정정).** 처음엔 PDP 방문 비콘이 국가 시드를 `visitedBrands` 게이트보다 **먼저** 심었다 — 브랜드관에서 국가를 이미 고른 손님이 제품을 클릭할 때마다 서버가 어차피 버릴 `track/country` 를 한 번씩 쏘는 걸 막으려는 것이었다(제품 5개 = 헛 POST 5개 + 헛 쿼리 10개). **그런데 그게 `trackStorefrontProductCountry` 를 통째로 도달 불가능하게 만들었다**: 국가를 **나중에** 고른 손님은 effect 가 재실행되며 게이트 앞에서 키만 찍고 곧바로 return 하므로, 뒤이은 국가 비콘이 자기 키에 막혀 **한 번도 안 나갔다** — 즉 이 항목이 살리려던 바로 그 딥링크 유입의 국가가 100% '미상'이었다. 지금은 키가 `id:{brandId}:{cc}` / `slug:{slug}:{cc}` **두 별칭**이고 브랜드관 비콘이 둘 다 찍어 같은 최적화를 대신하며, 표시(`markCountrySent`)는 **반드시 실제 전송과 같은 경로에서만** 한다. **시드를 게이트 위로 되돌리지 말 것.** ⚠️ **`promotionCode` 를 절대 싣지 않는다**(localStorage 영속값이라 예전 링크에 클릭이 영원히 붙는다). 현장(`?mode=onsite`)은 `brandMode` 가 false 라 자동 제외. ⚠️ **의도된 손실**: 딥링크 PDP 를 먼저 본 사람은 원장 `source` 가 `direct` 로 **고정**돼, 같은 날 할인 링크로 브랜드관에 와서 결제해도 그 결제가 `promotion` 이 아니라 `direct` 에 잡힌다("할인 링크 추이: 클릭 1"인데 "할인링크 탭: 방문자 0"으로 두 화면이 어긋나 보일 수 있다). `?mode=onsite` 가 이미 만든 것과 같은 성질이고, 고치려면 마지막-쓰기-승이 필요한데 그건 읽기 모델에 감산을 요구해 음수 카운터를 만든다 — **회귀 스펙이 이 동작을 의도된 손실로 명문화**해 뒀으니 "버그네" 하고 고치지 말 것. 불변식은 전부 유지된다(`uniqueCartAdds ≤ uniqueVisits` · `Σ국가 + 미상 == uniqueVisits` · `totals.all == direct + promotion`). ⚠️ 배포 순서는 **klow_server → klow_web**(프론트 2개는 배포 대상 아님) — **klow_web 을 먼저 내면 그 창의 PDP 방문이 통째로 유실된다.** 국가 수집 배포 때는 필드 *추가*라 구 서버가 unknown key 를 조용히 strip 했지만 여기는 **필수 필드 제거**라 구 서버 zod 가 400 을 내고 `api.ts` 의 `.catch(devWarn)` 이 프로덕션에서 삼킨다. **마이그레이션 없음 · cron 8개 불변 · 라우트 수 불변.** ⚠️ 배포 첫날 `uniqueVisits(direct)`·`purchases` 가 **계단처럼 올라간다**(딥링크 유입이 새로 들어온다 — 할인 링크 클릭이 봇 제외로 계단처럼 내려갔던 것과 같은 성질). 회귀 잠금은 `storefront-stats/__tests__/storefront-stats.spec.ts` PDP
